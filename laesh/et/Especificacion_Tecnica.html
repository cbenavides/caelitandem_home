2. Arquitectura del Sistema

El sistema opera bajo una arquitectura de tres capas con procesamiento distribuido entre el edge (dispositivos móviles) y el servidor central.

Los componentes principales son:

  • Capa Cliente (Edge): Interfaz renderizada por el servidor impulsada por HTMX y Vanilla JS. Evita la sobrecarga de Single Page Applications (SPAs) delegando el estado lógico al backend, pero manteniendo una experiencia fluida. Incluye un Buscador Inteligente unificado (autocompletado desde 5 caracteres por nombre o folio) y manejo de notificaciones visuales/sonoras en el navegador.
  • Capa de Aplicación (Flight PHP & Swoole): Flight PHP actúa como orquestador, despachando rutas y validando seguridad (RBAC). Swoole Server mantiene conexiones WebSocket abiertas para Notificaciones Instantáneas Bidireccionales: alertas con sonido (silbato) para recepción al crear órdenes, y notificaciones silenciosas para médicos al cargar resultados, ambas con enlaces directos. Además, expone un Panel de Administración (CMS frugal) para gestionar el contenido de la web pública (promociones, paquetes, banners).
  • Capa de Datos: MariaDB como motor relacional transaccional (con retención de historial de 5 años), asegurando integridad mediante catálogos (ej. Catálogo de Estados, Catálogo de Estudios cargado vía Excel). El File System gestiona el almacenamiento seguro y persistente de los archivos PDF (órdenes clínicas y resultados).

2.2. Flujo de Datos End-to-End

Broadcast Real-Time vía Websocket (WSS) Recepcion->>Recepcion: Reproduce silbato.mp3 y renderiza Burbuja UI Recepcion->>API: GET /ordenes/recientes (al hacer clic en burbuja) API-->>Recepcion: HTML con el nuevo registro Note over Recepcion,DB: Si el WS falla, al reconectar o refrescar el cliente jala de la tabla notificaciones

El flujo detallado es:

  1. Captura y Envío: El Médico completa el formulario de solicitud en su portal móvil/desktop. Al enviar, HTMX intercepta el evento y lanza una petición POST asíncrona (AJAX).
  2. Validación y Persistencia (QoS - Slow-Path): El servidor PHP-FPM recibe la solicitud, verifica el token de sesión y los permisos RBAC. Si es exitoso, graba de forma transaccional la orden y, **obligatoriamente antes de lanzar la notificación en tiempo real**, inserta una alerta marcada como no leída en la tabla notificaciones de MariaDB. Esto garantiza la integridad y entrega de la alerta en caso de desconexión del cliente.
  3. Inter-Process Communication (Bridge HTTP): El controlador de PHP-FPM envía una petición HTTP POST asíncrona no-bloqueante a la URL del contenedor de Swoole (http://swoole:9502/publish) compartiendo el folio y los metadatos de la notificación.
  4. Respuesta al Emisor: El backend PHP-FPM responde inmediatamente al Médico con un fragmento HTML de éxito (HTTP 200), cerrando su hilo de ejecución.
  5. Notificación Activa (QoS - Fast-Path): El servidor Swoole v6 recibe el POST HTTP por la red de Docker y realiza un broadcast por WebSocket (a través del túnel seguro de Apache) a los clientes Recepción suscritos. El navegador intercepta este payload, reproduce el silbato de alerta y renderiza la burbuja UI.

2.2.1. Ciclo de Vida General de una Petición HTTP / HTMX

  1. Disparo e Interceptación (Cliente): El usuario realiza una acción (ej. clic o envío). El motor de HTMX (Vanilla JS) intercepta el evento nativo del navegador, cancela la recarga completa de la página y empaqueta los datos de los formularios de forma asíncrona.
  2. Enrutamiento y Seguridad (Servidor - Apache/Flight): La petición HTTP llega a Apache 2.4 y es despachada por Flight PHP. Lo primero que ejecuta el controlador es la verificación de sesión y permisos a través del objeto PDO centralizado de Delight-PHP/Auth y las reglas del RBAC Personalizado. Si el usuario no tiene permisos, se detiene el flujo y se retorna un fragmento HTML de error.

⚠️ Regla de Oro para Redirecciones en Flight PHP:
Debido a que el sistema opera bajo una subcarpeta (ej. /laesh/ en la configuración LAN / localhost), el enrutador de Flight PHP autodetecta este contexto y lo añade dinámicamente como prefijo a todas las llamadas del método Flight::redirect().

Por tanto, al redirigir mediante programación:
  • Incorrecto: Flight::redirect('/laesh/login'); (Produce un desvío inválido a /laesh/laesh/login que desencadena errores 404).
  • Correcto: Flight::redirect('/login'); (Flight resolverá dinámicamente la URL física como /laesh/login en runtime).
La única excepción aplicable son las respuestas para peticiones HTMX manejadas desde el cliente mediante HTMX u otros métodos de red directos, donde se debe inyectar manualmente la ruta absoluta usando la cabecera HTTP nativa header("HX-Redirect: /laesh/");.

2.4. Mecanismo de Notificación Híbrido (Bridge PHP-Swoole & QoS)

Para asegurar una entrega garantizada de notificaciones críticas a los médicos y al personal de recepción sin la sobrecarga de un broker externo (como MQTT), se implementa una arquitectura híbrida desacoplada:

2.4.1. El Puente de Comunicación (PHP-FPM ➔ Swoole IPC)

Dado que Flight PHP corre bajo el ciclo de vida limitado de PHP-FPM en Apache, no puede mantener sockets abiertos. La interoperación entre entornos se resuelve mediante un Bridge HTTP asíncrono unidireccional:

// Flujo en Controlador (PHP-FPM)
// 1. Persiste el evento en la BD
$db->query("INSERT INTO notificaciones (user_id, mensaje, leido) VALUES (...)");
// 2. Dispara el HTTP POST interno a Swoole de forma no-bloqueante
\Common\Notifier::emit('nueva_orden', ['folio' => $folio]);

La clase \Common\Notifier realiza una llamada HTTP POST a http://swoole:9502/publish (dirección interna del contenedor Swoole en la red Docker) con un CURLOPT_TIMEOUT ultra-corto (máximo 2 segundos) para evitar congelar el hilo HTTP del cliente si el servidor de notificaciones estuviera inactivo.

2.4.2. Estrategia de QoS (Calidad de Servicio) de Aplicación

El protocolo WebSocket carece de un mecanismo nativo de QoS. Para resolver las pérdidas de paquetes debido a bloqueos de pantalla o cortes de red móvil en dispositivos médicos, se implementa una estrategia híbrida:

  • Slow-Path (Garantía de Persistencia): La tabla notificaciones de MariaDB es la Fuente Única de Verdad (SSOT). Toda alerta se escribe en base de datos en estado "no leído" antes de ser emitida.
  • Fast-Path (Entrega Inmediata): Swoole v6 recibe el POST en su puerto HTTP local, e inmediatamente hace broadcast por WebSocket a todos los usuarios conectados.
  • Sincronización Fallback: El cliente JS en el navegador cuenta con lógica de auto-reconexión con backoff exponencial. Al detectar un evento de reconexión exitoso del WebSocket, el cliente dispara automáticamente una consulta AJAX ligera (GET /notificaciones/pendientes) a Flight PHP para descargar de la BD cualquier alerta persistida que se haya perdido durante la desconexión.

3.3. Filosofía de Frugalidad del Stack

Para cumplir con los principios de desarrollo ligero y optimización de recursos locales, el ecosistema LAESH implementa dos patrones de frugalidad a nivel de software:

3.3.1. Cargador de Dependencias Compartido (Frugal Autoloader)

En lugar de instalar y duplicar de forma física las librerías vendor (Flight PHP, Delight Auth, League Plates) en el directorio de cada aplicación web, se diseñó un **Autoloader PSR-4 compartido** en laesh-swbldi/commons/autoload.php. Este cargador mapea las llamadas de dependencias externas directamente al subdirectorio paralelo restaurant/commons/libs/ de la red Docker:

// Mapeos del Autoloader en LAESH
$sharedLibsDir = __DIR__ . '/../../restaurant/commons/libs';
// ...
'League\\Plates\\'  => $sharedLibsDir . '/plates/',
'Delight\\Auth\\'   => $sharedLibsDir . '/auth/Delight/Auth/',
'Common\\'          => __DIR__ . '/', // Local a LAESH

Esto reduce la huella de almacenamiento en disco en más del 80% y evita el traslape o divergencia de dependencias de infraestructura entre los proyectos hermanos, manteniendo un único núcleo de bibliotecas estables compartidas.

3.3.2. Bootstrap Global Unificado (commons.php)

La inicialización del entorno se centraliza en laesh-swbldi/commons/commons.php, el cual realiza las siguientes operaciones transversales en cada llamada HTTP:

  • Parámetros de Sesión Seguros: Fuerza las directivas session.cookie_httponly = 1, session.use_only_cookies = 1 y un ciclo de vida extendido de cookies y recolector de basura de 24 horas (86,400s) para soportar sesiones persistentes en los portales clínicos.
  • Capturador Global de Fallos: Intercepta errores y excepciones de PHP mediante gestores nativos redireccionados a \Common\Logger, evitando mostrar trazas del sistema (stack traces) en producción y garantizando que se guarde un registro físico.
  • Inyección de Dependencias: Registra e inicializa Delight\Auth\Auth, el gestor de accesos RbacManager, Plates (views engine) y la conexión PDO singleton en el router Flight PHP.

3.3.3. Estrategia de Pool de Conexiones a Base de Datos (PHP-FPM)

Dada la arquitectura share-nothing de PHP bajo Apache/PHP-FPM, no existe un hilo centralizado de memoria para administrar pools tradicionales. Para evitar el costo de reconexión TCP (~5-30ms por petición HTMX) se aplica el atributo PDO::ATTR_PERSISTENT => true en la clase Common\DB:

  • Pool a nivel de Proceso FPM: Cada worker activo mantiene en caché la conexión a MariaDB. Al atender peticiones consecutivas, reutiliza la conexión abierta de forma transparente.
  • Aislamiento en Swoole v6: Si en futuras fases el servidor de WebSockets requiere consultar MariaDB directamente, se utilizará obligatoriamente la clase nativa Swoole\Database\PDOPool para arrendar conexiones por corrutina de manera segura sin colisionar el socket.

3.4. Configuración de HTMX en el Ecosistema Ligero

La adopción de HTMX permite construir una SPA (Single Page Application) ligera manteniendo el control del estado y del HTML en el servidor (Flight/Plates). Las directivas de integración clave son:

  • hx-boost: Habilitado globalmente para interceptar todas las etiquetas y formularios de la aplicación, convirtiendo las recargas tradicionales en llamadas HTMX transparentes.
  • Intercambios Fuera de Banda (OOB): Utilizado activamente (hx-swap-oob="true") para actualizar elementos de interfaz remotos (ej. barra de estado del recepción, breadcrumbs, totales del día) en una única respuesta HTTP, sin necesidad de realizar múltiples peticiones HTMX paralelas.
  • Control de Retroalimentación de UI: Se configuran las clases .htmx-request y hx-indicator para activar automáticamente spinners e indicadores de carga globales, previniendo la frustración del usuario en llamadas lentas.

5.1. Generación Dinámica de Solicitudes Digitales (On-The-Fly)

Para maximizar la frugalidad de almacenamiento en el servidor local de la clínica, las solicitudes de laboratorio expedidas digitalmente por el médico hacia el paciente no se guardan como archivos PDF físicos en disco. En su lugar:

  • Renderizado al Vuelo: Al acceder al enlace o token web de la solicitud (ej. /solicitud/imprimir/{folio}), el motor de plantillas de Flight PHP (Plates) consulta las tablas ordenes y detalle_ordenes para renderizar la vista HTML optimizada para impresión/descarga en el dispositivo del usuario.
  • Ventajas del Modelo: Garantiza que cualquier cambio posterior en los datos del paciente o en el catálogo de estudios se refleje inmediatamente en el documento, evitando la acumulación de archivos estáticos obsoletos.

5.2. Gestión Paramétrica y Depuración de PDFs de Resultados (Retención de 8 Meses)

A diferencia de las solicitudes dinámicas, los archivos PDF de resultados adjuntos por el personal de laboratorio sí se almacenan en el sistema de archivos del servidor bajo un esquema paramétrico y con políticas de rotación estrictas:

  • Metadatos en BD (resultados_pdf): La tabla almacena el nombre_archivo original o normalizado (ej. Resultado_LAESH-00001.pdf) y la fecha_subida.
  • Ruta Base Paramétrica (configuraciones): La ruta absoluta donde se guardan físicamente los archivos se lee dinámicamente de la tabla configuraciones (clave = 'ruta_almacenamiento_pdf').
  • Politica de Depuración Automática (8 Meses): El parámetro de retención se configura en la tabla configuraciones (clave = 'tiempo_depuracion_pdf_meses' con valor por defecto de 8). Un proceso cron de mantenimiento programado ejecutará mensualmente el purgado físico de los archivos cuya fecha_subida supere los 8 meses, eliminando también su registro correspondiente en resultados_pdf.

6. Observabilidad y Trazabilidad de Fallos (Logs y Auditoría)

Siguiendo la directiva de robustez y resiliencia en entornos de red y base de datos locales inestables, el ecosistema LAESH cuenta con dos clases helper dentro del espacio de nombres \Common para el registro de auditoría, trazabilidad SQL y telemetría:

6.1. Log General del Sistema (Common\Logger)

La clase \Common\Logger gestiona la ingesta de alertas generales de la aplicación (INFO, WARN, ERROR, FATAL) mediante una arquitectura de persistencia redundante (Dual‑Path):

  • Ruta de Base de Datos (sys_logs): Guarda el nivel de severidad, mensaje, marca temporal de forma centralizada y la dirección IP del cliente. También asocia opcionalmente el user_id de la sesión de Delight PHP Auth para rastreo del operador.
  • Ruta Fallback Física (logs/app.log): Si la base de datos está offline o no responde, el log se redirige de forma automática hacia un archivo de respaldo local plano para prevenir la pérdida de datos del sistema.

6.2. Trazabilidad y Telemetría de Fallos SQL (Common\DB::logFallback)

Inspirado en el motor de mitigación de fallos de Agua, la clase \Common\DB intercepta y registra de forma segura los fallos en la ejecución de transacciones y queries PDO:

  • Uso de Debug Backtrace: Emplea debug_backtrace() para indagar en la pila de ejecución y extraer automáticamente el archivo físico y la línea exacta de código que detonó la consulta (omitiendo los frames internos de la clase de base de datos).
  • Hash de Agrupamiento (CRC32): Genera un hash único de 8 caracteres hexadecimales derivado del CRC32 del string SQL original. Esto permite agrupar y contar incidencias duplicadas en los reportes de auditoría técnica.
  • Estructura fallback_log: Los registros fallidos se guardan en la tabla fallback_log con el texto SQL completo, el error nativo arrojado por el driver PDO (errorInfo) y el número de filas afectadas en operaciones de escritura.

6.3. Esqueleto de Integración en Controladores

Ejemplo de uso de trazabilidad en la captura y tratamiento de excepciones dentro de una ruta de API en Flight PHP:

Flight::route('POST /estudio/resultado', function() {
    $ordenId = Flight::request()->data->orden_id;
    $filePath = Flight::request()->data->file_path;
    $userId = Flight::auth()->getUserId();

    try {
        // Ejecución transaccional
        $db = \Common\DB::connect();
        $db->beginTransaction();

        $stmt = $db->prepare("CALL ProcesarCargaResultadoPDF(:orden_id, :file_path)");
        $stmt->execute([':orden_id' => $ordenId, ':file_path' => $filePath]);

        $db->commit();
        \Common\Logger::log('INFO', "PDF cargado para orden ID: $ordenId", $userId);

        echo json_encode(['status' => 'success']);
    } catch (\PDOException $e) {
        if (isset($db)) $db->rollBack();

        // 1. Registra el fallo específico del query en fallback_log
        \Common\DB::logFallback('ERROR', "CALL ProcesarCargaResultadoPDF($ordenId, $filePath)", $e->getMessage());

        // 2. Registra la alerta de observabilidad general
        \Common\Logger::log('ERROR', "Fallo al subir resultado PDF para orden: $ordenId", $userId);

        Flight::halt(500, json_encode(['error' => 'Error interno al guardar resultados']));
    }
});

6.4. Trazas y Logs de Depuración para Desarrollo (Entornos de Test)

Para facilitar las tareas de depuración en tiempo de desarrollo y pruebas de integración, se cuenta con dos alternativas de logging configurables:

6.4.1. Alternativa 1: Registro Centralizado del Proyecto (\Common\Logger)

Recomendado para almacenar de forma persistente eventos significativos del sistema o volcar estructuras complejas de datos. Esta alternativa escribe redundantemente en la tabla sys_logs y en el archivo de texto plano local del proyecto laesh-swbldi/logs/app.log.

  • Uso Básico: 
    // Mensaje informativo simple
\Common\Logger::log('INFO', 'Procesando el cálculo de nómina.');

// Volcado de arreglos u objetos para depuración
$datosDepuracion = ['paciente_id' => 12, 'estudios' => [1, 5, 8]];
\Common\Logger::log('DEBUG', 'Volcado de variables: ' . print_r($datosDepuracion, true));
  • Monitoreo en Vivo (Consola): Desde la terminal del desarrollador se puede visualizar el log físico de la aplicación en tiempo real ejecutando: 
    tail -f /home/carlos/GitHub/caelitandem_home/restaurantb/www/laesh-swbldi/logs/app.log

6.4.2. Alternativa 2: Log de Errores Nativo de PHP (error_log)

Recomendado para depuración veloz en caliente y de corta duración, omitiendo la escritura en base de datos.

  • Uso Básico: 
    error_log("DEBUG: Valor temporal de token: " . $token);
  • Monitoreo en Vivo (Consola): Al estar configurado PHP bajo un entorno de contenedores Docker, la salida de error_log es enviada al descriptor stderr del proceso. Se puede ver en tiempo real con el comando: 
    docker compose logs -f laesh_swoole # O bien restaurantb_web
