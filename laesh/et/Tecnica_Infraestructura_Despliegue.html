B.2) Estado de hecho en laptops y computadoras en LAN
B.3) Uso de setup-ssl.sh en Cambios de Host o de IP (Recomendado)
  1. Asegúrate de tener mkcert instalado en el sistema host (sudo apt update && sudo apt install -y mkcert).
  2. Posteriormente, descarga la nueva CA raíz en cada teléfono Android desde la nueva IP e instálala en la sección de Seguridad.
B.4) Método Alternativo Manual Paso a Paso

Si prefieres realizar el procedimiento de forma manual:

  1. Instale mkcert en el servidor local (ej: sudo apt install mkcert).
  2. Genere la Autoridad Certificadora local: mkcert -install.
  3. Cree los certificados para la nueva IP (ej. 192.168.1.100):
    mkcert -cert-file ../ssl/server.crt -key-file ../ssl/server.key 192.168.1.100 localhost 127.0.0.1.
  4. Reemplace los archivos generados en la carpeta ssl/ del host (que se monta en /etc/apache2/ssl en el contenedor web).
  5. Copie el certificado de la CA raíz pública (~/.local/share/mkcert/rootCA.pem) como www/ca.crt para permitir su descarga por red.
  6. Reinicie el contenedor de Apache: docker compose restart web.
  7. Instale el archivo ca.crt generado como Certificado de CA en los teléfonos clientes Android de prueba.

11. Seguridad, Resiliencia y Observabilidad

11.1. Protección Activa

  • Validación de entradas: Sanitización de datos en todos los endpoints para prevenir SQL injection (uso estricto de PDO prepare/execute).
  • Backup automático: Script cron cada hora: mysqldump órdenes_db > /backup/órdenes_$(date +%Y%m%d_%H).sql

11.1.5. Observabilidad (Telemetría y Logging)

La salud del sistema offline se monitoriza a través de un esquema estructurado (estilo Log4j / PSR-3) que garantiza la trazabilidad convergente:

  • Cola offline: órdenes se almacenan en IndexedDB ante pérdida de Wi-Fi y se sincronizan al restaurar.
  • UPS recomendado: 600VA+ para protección ante cortes eléctricos.

11.3. Privacidad

  • Datos almacenados mínimos: Solo texto transcrito, hora y productos. Sin biométricos ni datos sensibles de clientes.
  • Control local: Todos los datos residen físicamente en el servidor del laeshe.
→ Ver Issues Conocidos y Mitigaciones

11.5. Control Cronológico y Mitigación de Desfases (Marcas de Tiempo)

  • Al restaurar la conexión, el Service Worker transmite el payload con el valor acumulado de duracion_offline_ms.
  • El servidor calcula el instante real del registro restando el tiempo offline del instante de recepción: 
    Hora_Real_Registro = server_received_time - duracion_offline_ms
