Propuesta de Evolución: Migración a App Nativa Android (Kotlin)

Contexto de la Propuesta: La implementación actual de reconocimiento de voz offline (VOSK) funciona bajo el paradigma de una PWA (Progressive Web App). Aunque funcional gracias a severos workarounds (Kill-and-Respawn, WakeLock y limpieza forzada del motor WASM), la naturaleza del navegador móvil impone restricciones infranqueables que penalizan el hardware de las tabletas (OOM, Sobrecalentamiento) e impiden la captura de audio en segundo plano (pantalla apagada o tablet en el bolsillo).

1. Análisis Comparativo: PWA (WASM) vs Nativo (Kotlin AAR)

Característica / Limitante Estado Actual (PWA Web) Solución Nativa (Kotlin Android)
Gestión de Memoria y Basura WASM Heap lineal. Requiere destruir y recrear la instancia del reconocedor (Kill-and-Respawn) para vaciar la RAM (Riesgo OOM). Uso de .aar oficial JNI. Liberación de punteros en C++ orquestada limpiamente por la JVM de Android. Cero OOMs.
Uso en Bolsillo (Pantalla Apagada) Bloqueado por el Navegador (Políticas Chrome). Si se apaga la pantalla, se corta el micrófono y la red. Plena compatibilidad mediante ForegroundService con notificación persistente. El mesero dicta con la tablet guardada.
Multihilo y Rendimiento CPU Monohilo estricto simulado. Riesgo alto de Thermal Throttling (lag al calentar el dispositivo). Corrutinas verdaderas (Dispatchers.IO) que operan fuera del Main Thread. Aprovechamiento de todos los núcleos del hardware.
Consumo de Batería Altísimo. Requerimos WakeLock forzado (mantiene la pantalla viva a la fuerza). Bajísimo. Uso de hardware de audio de bajo nivel de Android y pantalla apagada permitida.

2. Hoja de Ruta de Alto Nivel para la Portabilidad (Roadmap)

Fase 1: Configuración de la Arquitectura Android

  • Inicialización del Proyecto: Crear proyecto en Android Studio usando Kotlin y Jetpack Compose para la UI.
  • Integración de Dependencias VOSK: Añadir el archivo .aar de alphacep/vosk-android. Embeber el mismo modelo acústico (Small ES 0.42) comprimido dentro de la carpeta assets/.
  • Permisos: Configurar el AndroidManifest.xml solicitando permisos críticos: RECORD_AUDIO, INTERNET y FOREGROUND_SERVICE_MICROPHONE.

Fase 2: Arquitectura Clean (Core de Voz)

  • Desarrollo del ViewModel y Corrutinas: Migrar la lógica de app-voice.js a un VoiceViewModel usando flujos reactivos (StateFlow) para que la UI observe el estado (Cargando, Escuchando, Comando Parcial).
  • Servicio en Segundo Plano (Foreground Service): Crear un servicio nativo de Android vinculado a una notificación adhesiva. Este servicio contendrá la instancia del SpeechService de Vosk, garantizando que el S.O. no lo mate en el bolsillo.
  • Levenshtein y NLP Nativo: Portar los algoritmos de Levenshtein, limpieza de tildes y mapeo del vocabulario a clases utilitarias (Utils) de Kotlin.

Fase 3: Sincronización y Backend de Red

  • Integración de Retrofit/OkHttp: Configurar el cliente HTTP para comunicación con el backend (Host A/C) local (192.168.x.x) a través de Endpoints REST/JSON.
  • Catálogo Offline (Room Database): Reemplazar IndexedDB (Dexie.js) con Room (SQLite Nativo de Android). Sincronizar el catálogo, alias y metadatos usando la misma lógica de delta hash que usamos hoy.

Fase 4: Interfaz de Usuario y Q.A.

  • Recreación de las Vistas Híbridas: Diseñar la KDS (Cocina) y la vista de Meseros (Toma de órdenes) usando componentes nativos de Jetpack Compose imitando el Glassmorphism si se desea, pero con un rendimiento fluido a 60fps.
  • Manejo de TTS (Text-to-Speech): Migrar Web Speech API a la API nativa de Android TextToSpeech (TTS). Es muchísimo más rápida, libre del límite de "15 segundos" de Chrome, y más confiable para notificaciones de la cocina.
  • Pruebas de Resistencia: Mantener la tableta apagada conectada a WiFi durante 8 horas y disparar 500 comandas habladas de prueba automatizada para confirmar la ausencia de cuellos de botella térmicos (OOM).

3. Conclusión Estratégica

Migrar a Kotlin resolverá definitivamente el 100% de los issues operacionales (Calentamiento térmico, drenaje de batería y "El gap de la pantalla apagada") eliminando los "workarounds" efímeros de WASM. A nivel funcional, abrirá la puerta para que el staff de piso utilice la herramienta de forma invisible y transparente, logrando un reconocimiento de voz casi militarizado para ambientes ruidosos.
