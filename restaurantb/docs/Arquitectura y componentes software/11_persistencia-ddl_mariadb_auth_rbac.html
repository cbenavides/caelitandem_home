Diseño de Persistencia: Esquema Relacional de Seguridad (MariaDB 11)

Para soportar el stack ligero, el motor de base de datos MariaDB 11 implementa un esquema híbrido. Por un lado, mantiene las tablas estandarizadas requeridas por la API criptográfica de Delight-PHP/Auth; por el otro, extiende la estructura con una solución relacional ágil para el control de accesos basado en roles (RBAC Personalizado) que será consultada en el backend mediante Medoo.

1. Tablas Base del Motor de Autenticación (Delight-PHP/Auth)

Estas tablas gestionan los estados de login, persistencia de sesiones ("recuérdame"), solicitudes de restablecimiento de contraseña por correo y mitigación de ataques de fuerza bruta:

1.1. Tabla Principal de Cuentas (users)

CREATE TABLE IF NOT EXISTS `users` (
  `id` int(10) unsigned NOT NULL AUTO_INCREMENT,
  `email` varchar(249) COLLATE utf8mb4_unicode_ci NOT NULL,
  `password` varchar(255) CHARACTER SET latin1 COLLATE latin1_general_cs NOT NULL,
  `username` varchar(100) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `status` tinyint(3) unsigned NOT NULL DEFAULT '0',
  `verified` tinyint(3) unsigned NOT NULL DEFAULT '0',
  `resettable` tinyint(3) unsigned NOT NULL DEFAULT '1',
  `roles_mask` int(10) unsigned NOT NULL DEFAULT '0',
  `registered` int(10) unsigned NOT NULL,
  `last_login` int(10) unsigned DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `email` (`email`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

1.2. Tabla de Persistencia de Sesiones Permanentes (users_remembered)

CREATE TABLE IF NOT EXISTS `users_remembered` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT,
  `user` int(10) unsigned NOT NULL,
  `selector` varchar(24) CHARACTER SET latin1 COLLATE latin1_general_cs NOT NULL,
  `token` varchar(255) CHARACTER SET latin1 COLLATE latin1_general_cs NOT NULL,
  `expires` int(10) unsigned NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `selector` (`selector`),
  KEY `user` (`user`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

1.3. Tabla de Control de Fuerza Bruta y Rate Limiting (users_throttling)

CREATE TABLE IF NOT EXISTS `users_throttling` (
  `bucket` varchar(44) CHARACTER SET latin1 COLLATE latin1_general_cs NOT NULL,
  `tokens` float unsigned NOT NULL,
  `replenished_at` int(10) unsigned NOT NULL,
  `expires_at` int(10) unsigned NOT NULL,
  PRIMARY KEY (`bucket`),
  KEY `expires_at` (`expires_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

2. Extensiones del Sistema RBAC Personalizado

Para implementar una autorización limpia consultable desde las vistas de Plates y formularios de HTMX, se desacoplan los permisos planos de la máscara de bits nativa de Delight-Auth, creando una estructura relacional óptima:

2.1. Catálogo de Permisos del Sistema (rbac_permisos)

Define de manera única las acciones o capacidades atómicas de la WebApp (ej: CREAR_PEDIDOS, ANULAR_TRANSACCION):

CREATE TABLE IF NOT EXISTS `rbac_permisos` (
  `id` int(10) unsigned NOT NULL AUTO_INCREMENT,
  `nombre` varchar(60) COLLATE utf8mb4_unicode_ci NOT NULL,
  `descripcion` varchar(255) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `idx_permiso_nombre` (`nombre`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

2.2. Relación Intermedia de Permisos por Usuario (rbac_permisos_usuarios)

Asocia directamente las capacidades atómicas con el identificador de cuenta de Delight-Auth. Permite añadir o revocar privilegios específicos a usuarios individuales de manera dinámica:

CREATE TABLE IF NOT EXISTS `rbac_permisos_usuarios` (
  `user_id` int(10) unsigned NOT NULL,
  `permiso_id` int(10) unsigned NOT NULL,
  `asignado_el` timestamp NOT NULL DEFAULT current_timestamp(),
  PRIMARY KEY (`user_id`, `permiso_id`),
  CONSTRAINT `fk_rbac_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_rbac_permiso` FOREIGN KEY (`permiso_id`) REFERENCES `rbac_permisos` (`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

3. Directiva Operativa de Consulta (Indexación y Rendimiento)

Para asegurar que las comprobaciones de autorización ejecutadas por el método mapeado en Flight PHP no penalicen el rendimiento de Apache:

  • La clave primaria compuesta de rbac_permisos_usuarios genera automáticamente un índice ordenado agrupado por user_id. Esto garantiza que las búsquedas booleanas rápidas tipo $db->has() de Medoo se resuelvan en tiempo sub-milisegundo.
  • Las operaciones de asignación masiva de permisos deben consolidarse en el backend o delegarse a procedimientos almacenados si alteran de manera secuencial los flujos de auditoría del negocio gastronómico o comercial.
