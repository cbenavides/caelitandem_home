Especificación de Arquitectura: Estrategias Offline y Caché (PWA)

Para asegurar que una WebApp ligera con backend en PHP sea considerada una PWA (Progressive Web App) real, el Service Worker Nativo debe tomar el control total de la red en el navegador (Chrome). Su misión es interceptar todas las peticiones, discriminar qué archivos se guardan localmente y definir cómo responder cuando el usuario no tiene conexión a internet.

1. Ciclo de Vida y Políticas de Almacenamiento en Caché

No todos los recursos de la WebApp se tratan igual. El Service Worker gestiona el almacenamiento dividiendo la aplicación en dos grandes categorías utilizando la API nativa CacheStorage:

  • El "App Shell" (Estructura Base): Archivos estáticos indispensables para que la aplicación cargue visualmente (el CSS global, el logo, el archivo JavaScript de HTMX, Dexie.js y tu app.js). Estos archivos se descargan e instalan de forma permanente la primera vez que el usuario abre la aplicación.
  • Las Vistas Dinámicas (Fragmentos HTML): Las páginas o módulos generados por Plates en el servidor Apache se gestionan con políticas de expiración temporal para evitar que el usuario vea información vieja cuando recupere la conexión.

2. Estrategias de Red del Service Worker

Para lograr la mejor velocidad combinada con disponibilidad sin internet, el Service Worker implementa dos estrategias de red específicas:

Estrategia A: Cache First / Network Fallback (Para el App Shell)

¿Cómo funciona? Cuando el navegador solicita los scripts esenciales (como htmx.min.js o los estilos CSS), el Service Worker busca primero en la caché local de Chrome. Si el archivo está ahí, lo entrega de inmediato (en milisegundos, sin tocar internet). Solo si el archivo no existe en la caché, sale a buscarlo al servidor Apache.

¿Para qué sirve? Hace que la WebApp encienda de manera instantánea en el dispositivo del usuario, exactamente igual que una aplicación móvil nativa, consumiendo cero datos móviles en sus arranques diarios.

Estrategia B: Network First / Cache Fallback (Para Datos y Vistas de Plates)

¿Cómo funciona? Cuando el usuario navega por los módulos (ej. ver el listado de clientes), el Service Worker intenta ir primero al servidor Apache mediante la red. Si el servidor responde con éxito, actualiza la copia local en la caché y le muestra los datos frescos al usuario. Si la red falla (el usuario entró a un sótano o no tiene señal), el Service Worker intercepta el fallo y rescata de la caché el último HTML que Plates había generado previamente.

¿Para qué sirve? Garantiza que la aplicación nunca muestre la pantalla de error de Chrome ("Sin conexión"). En su lugar, el operario puede seguir consultando la información con la que trabajó minutos atrás.

3. Sincronización Fuera de Línea (Garantía de Idempotencia de Datos)

El mayor reto de una arquitectura basada en HTML asíncrono ocurre cuando el usuario intenta enviar un formulario (un POST) estando completamente Offline. Dado que las cachés de los navegadores solo guardan peticiones de lectura (GET), las escrituras se resuelven mediante la cooperación entre HTMX y la base de datos local.

El Flujo de Sincronización en Segundo Plano:

  1. Interceptación de HTMX: Al hacer clic en un botón para enviar datos, el archivo app.js escucha el evento global htmx:configRequest y detecta si el navegador está fuera de línea (navigator.onLine === false).
  2. Cancelación y Resguardo Local: HTMX detiene la petición antes de que viaje por la red. El script del cliente toma los datos del formulario y los inserta inmediatamente de forma estructurada en la IndexedDB de Chrome utilizando la sintaxis limpia de Dexie.js. La operación queda marcada en una tabla local llamada cola_peticiones_pendientes.
  3. Activación del Background Sync: El script le avisa al Service Worker nativo que registre un evento de sincronización de fondo (syncManager). El Service Worker se queda dormido esperando a que el sistema operativo del teléfono o computadora detecte internet de alta calidad.
  4. Sincronización Silenciosa y Segura: Cuando el internet regresa (incluso si el usuario cerró la pestaña de la WebApp), el Service Worker se despierta en segundo plano. Lee las peticiones acumuladas en Dexie.js y las envía en orden cronológico mediante un fetch() nativo de Vanilla JS hacia el endpoint de Flight PHP en el servidor.
  5. Procesamiento en Servidor: El backend procesa las solicitudes una por una, validando sus tokens de idempotencia para asegurar que ninguna se inserte por duplicado en MariaDB 11, y limpia la cola en la IndexedDB una vez confirmado el éxito.
