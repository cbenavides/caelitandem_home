3. Especificación Técnica de HTMX en el Ecosistema Ligero

HTMX funciona como el orquestador principal del comportamiento interactivo y de seguridad en el lado del cliente (Chrome), comunicándose de forma nativa con el servidor a través de los siguientes pilares:

3.1. Soporte para AJAX Nativo y Manipulación del DOM

  • Abstracción Completa: Ejecuta llamadas asíncronas utilizando fetch() de Vanilla JS bajo atributos como hx-get, hx-post, hx-put y hx-delete.
  • Inyección Directa: Recibe código HTML crudo pre-renderizado por Plates y lo acopla en el elemento destino especificado en hx-target utilizando el motor interno de intercambio rápido (hx-swap), reduciendo la necesidad de serializar o procesar JSON en el cliente.

3.2. Comunicación en Tiempo Real vía WebSockets (WS)

  • Persistencia de Canal: Mediante su extensión oficial de WebSockets (ext/ws), HTMX se conecta al puerto del servidor asíncrono de Swoole de manera transparente.
  • Intercambio Fuera de Banda Dinámico: Permite que Swoole envíe de forma proactiva (Push) fragmentos de HTML cuando ocurren eventos del servidor (o respuestas del contenedor de IA de Voz Vosk) e inyectarlos de inmediato en zonas específicas de la pantalla utilizando la directiva hx-swap-oob="true".

3.3. Integración con Autenticación (Auth) y Sesión HTTP

  • Transporte Seguro de Cookies: Al estar construido sobre Vanilla JS puro, HTMX incluye automáticamente las cabeceras nativas de cookies y la sesión activa de PHP (PHPSESSID) en todas las peticiones asíncronas de red, manteniendo la persistencia transparente con Delight-PHP/Auth.
  • Ciclo Multi-Sesión por Pestaña: Si se requiere aislamiento total por pestañas usando Tokens JWT guardados en sessionStorage, HTMX expone el evento global htmx:configRequest para interceptar la petición de red e inyectar dinámicamente las cabeceras de autorización (Authorization: Bearer [token]) de forma automatizada.

3.4. Integración con la Autorización (Authz) y el Sistema RBAC

  • Control de Flujos de Error (HTTP 401/403): Cuando el sistema RBAC personalizado en el servidor determina que el usuario no tiene permisos e interrumpe una petición a través de Flight, HTMX captura el código de estado HTTP erróneo mediante eventos como htmx:responseError.
  • Respuestas Seguras de Interfaz: Permite redirigir automáticamente la interfaz completa al login si expira la sesión (leyendo la cabecera HX-Redirect enviada por el controlador PHP) o renderizar una alerta de denegación de acceso local de forma limpia e instantánea.

4. Estrategia de Persistencia y Criterios de Uso de Medoo

Para mantener el servidor backend liviano y veloz, se establece una división clara en la estrategia de base de datos entre la manipulación rápida de datos en PHP y la lógica procedural en MariaDB 11:

4.1. Escenarios de Uso de Medoo Nativo (Consultas Comunes y Típicas)

  • Inserciones, Actualizaciones y Borrados Simples: Uso directo de los métodos $db->insert(), $db->update() y $db->delete(), lo que garantiza protección automatizada contra inyecciones SQL mediante Prepared Statements sin sobrecarga de código.
  • Lecturas y Validaciones de Existencia: Uso de $db->get() y $db->has() para tareas cotidianas rápidas, como verificar las credenciales básicas de Delight-PHP/Auth o comprobar de forma directa si un usuario posee un permiso plano en la tabla relacional del RBAC.
  • Listados Directos sin Relaciones Complejas: Uso de $db->select() para alimentar tablas sencillas que se enviarán a Plates, manteniendo un bajo consumo de memoria RAM en el proceso de Apache.

4.2. Escenarios de Uso de Stored Procedures (Consultas Complejas, JOINS y Transacciones)

  • JOINS Pesados y Reportes Multi-Tabla: Cuando se requiera cruzar múltiples tablas de negocio con filtros dinámicos u ordenamientos complejos, la consulta se encapsulará en un Stored Procedure. Medoo actuará únicamente como el despachador seguro mediante su método $db->query("CALL ObtenerReportePesado(:param)", [...])->fetchAll().
  • Garantía de Integridad y Transacciones de Negocio: Las operaciones que involucren múltiples escrituras dependientes se procesarán dentro de bloques START TRANSACTION y COMMIT/ROLLBACK nativos en el Stored Procedure de MariaDB. Esto blinda al sistema contra fallas parciales si la conexión Apache-PHP se interrumpe a mitad de una transacción.
  • Seguridad de Abstracción de Datos: Al encapsular la lógica de negocio compleja en procedimientos almacenados, el código en Flight PHP se mantiene sumamente limpio y ordenado, evitando exponer la estructura física interna de las tablas en los archivos PHP de la WebApp.

4.3. Directiva de Refactorización y Reúso de Conectividad Legacy

Para construir la infraestructura de conectividad optimizada hacia la base de datos utilizando Medoo, es obligatorio realizar una auditoría profunda y extracción de lógica útil de los siguientes archivos del sistema anterior:

  • /home/carlos/GitHub/caelitandem_home/restaurantb/www/restaurant/sistema/Conexion.php
  • /home/carlos/GitHub/caelitandem_home/restaurantb/www/restaurant/sistema/config.php

Criterios de Adaptación y Refactorización Mandatorios:

  • Reúso de Parámetros y Estados de Sesión: Se deben extraer las configuraciones de entorno del archivo config.php e integrar los comandos de sesión iniciales del motor de base de datos presentes en Conexion.php, tales como SET SESSION sql_mode u optimizaciones de aislamiento de transacciones de MariaDB, inyectándolos dentro del arreglo de configuración u opciones PDO::ATTR_INIT_COMMAND al inicializar el objeto de Medoo.
  • Migración del Mecanismo de Resiliencia: Se debe refactorizar la lógica de control de errores y logs secundarios (_logFallback) detectada en los archivos legacy. Este flujo se adaptará al bloque global de manejo de excepciones del nuevo proveedor de datos, asegurando que si ocurre un fallo crítico de conexión en Apache, el sistema registre el incidente e invoque una respuesta controlada de contingencia hacia la WebApp/PWA.
  • Pool de Conexiones y Sanitización: Se analizará el comportamiento del pool de conexiones persistentes (si aplica) de la clase anterior para replicarlo mediante los atributos nativos de PDO en Medoo (PDO::ATTR_PERSISTENT). Asimismo, las funciones manuales de escape de valores (Escaped values) usadas previamente para la seguridad de sentencias INSERT serán eliminadas y sustituidas al 100% por los marcadores de posición parametrizados automatizados de Medoo, garantizando inmunidad contra inyección SQL.
