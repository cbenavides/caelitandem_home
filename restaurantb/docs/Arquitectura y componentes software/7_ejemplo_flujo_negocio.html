Especificación de Interoperación: Caso de Uso Real

Caso Práctico: Creación de Pedido por Dictado de Voz Inteligente

Este escenario describe el flujo de datos exacto cuando un usuario con rol de "Operario" presiona un botón, dicta un comando de voz (ej: "Registrar pedido de 50 unidades"), el sistema lo procesa con Inteligencia Artificial, guarda la información en la base de datos de forma segura y actualiza la pantalla junto con las notificaciones push.

Fase 1: Interacción Inicial en el Navegador

  • El operario carga la interfaz generada originalmente por el motor de vistas Plates.
  • Presiona el botón de micrófono. Un script de Vanilla JS activa la API nativa de audio de Chrome para capturar los fragmentos binarios de voz del operario.
⬇️

Fase 2: Procesamiento Concurrente de IA en el Servidor

  • El script de cliente transmite el flujo de audio asíncronamente abriendo un canal persistente hacia el servidor independiente de Swoole.
  • Swoole (corriendo de forma persistente en CLI) recibe los datos binarios de red y abre una conexión directa por sockets de alta velocidad hacia el contenedor aislado de alphacep/kaldi-es (Vosk).
  • La IA de Vosk procesa el audio localmente y le devuelve a Swoole el texto plano transcribido: "Registrar pedido de 50 unidades".
  • Swoole envía el texto de vuelta al navegador a través del mismo WebSocket.
⬇️

Fase 3: Ejecución Transaccional en el Backend

  • Al recibir el texto transcribido, HTMX entra en acción automáticamente simulando un envío seguro de formulario enviando un POST hacia la ruta de control /pedidos/crear administrada por Flight PHP.
  • El formulario de HTMX adjunta un token criptográfico único e invisible para asegurar la idempotencia.
  • Flight PHP recibe la petición e invoca a Delight-PHP/Auth junto con las tablas de permisos del RBAC personalizado para cerciorarse de que el usuario logueado posee el permiso de escritura CREAR_PEDIDOS.
  • Validada la seguridad, el controlador invoca a Medoo, el cual ejecuta un Stored Procedure en MariaDB 11 que inserta el pedido, actualiza los inventarios y confirma la transacción de forma aislada y segura contra fallas de red.
⬇️

Fase 4: Respuesta de Interfaz y Notificación Push

  • Tras el éxito en MariaDB, Flight PHP le solicita a Plates renderizar solo el fragmento de la nueva fila de la tabla de pedidos.
  • Al final del archivo de Plates, se incluye un bloque HTML con el atributo hx-swap-oob="true" conteniendo las nuevas migas de pan actualizadas (Inicio / Pedidos / Creado Exitosamente).
  • HTMX recibe la respuesta asíncrona, inyecta la nueva fila en la tabla de pedidos, actualiza los breadcrumbs externos y apaga el indicador visual de carga (spinner).
  • Paralelamente, el servidor envía un evento push global. El Service Worker Nativo del navegador despierta en segundo plano y muestra una notificación nativa en la pantalla del usuario confirmando el registro del pedido, incluso si cambió de pestaña.
