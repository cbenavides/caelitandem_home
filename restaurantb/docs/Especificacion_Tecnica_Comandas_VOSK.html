1. Resumen Ejecutivo Técnico

El presente documento establece las especificaciones técnicas de implementación para un sistema de comandas por reconocimiento de voz offline basado en el motor VOSK. El sistema opera íntegramente sobre infraestructura local con PHP 8.x, MariaDB y Ubuntu Server 22.04 LTS.

La arquitectura se fundamenta en tres pilares técnicos diferenciadores: (1) el reconocimiento de voz 100% offline mediante WebAssembly en el navegador del dispositivo Android del mesero, (2) la interacción exclusiva por voz del cocinero mediante diadema con gramática ultra-restringida, y (3) la síntesis de voz (TTS) para anuncios en altavoz de cocina y respuestas en diademas. El sistema no procesa métodos de pago; calcula totales y genera tickets impresos únicamente.

El procesamiento de audio se ejecuta en el edge (dispositivo del mesero/cocinero) mediante WebAssembly, distribuyendo la carga computacional y eliminando dependencias de servicios cloud. Las comandas se transmiten vía HTTPS a un servidor local LAMP sobre Ubuntu 22.04, donde PHP-FPM gestiona la lógica de negocio y MariaDB persiste los datos transaccionales.

Pilares Tecnológicos del Sistema

  • Edge computing con VOSK/WASM: Transcripción de voz local en el navegador del dispositivo Android.
  • Interfaz 100% voz para cocina: Gramática ultra-restringida para reconocimiento de comandos del cocinero.
  • TTS (Text-to-Speech): Anuncios en altavoz de cocina y respuestas en diademas Bluetooth.
  • Cola offline con IndexedDB: Persistencia local de comandas ante fallas de red Wi-Fi.
  • Arquitectura frugal LAMP: Servidor único con Ubuntu 22.04, Apache, PHP-FPM, MariaDB.

2.2. Flujo de Datos End-to-End

Figura 2. Flujo de datos completo incluyendo canales TTS

El flujo detallado es:

  1. Captura de audio: El mesero dicta a su diadema Bluetooth. El AudioWorklet del navegador captura audio PCM a 16 kHz mono.
  2. Procesamiento local: El Web Worker de VOSK (WASM) transcribe el audio a texto usando el modelo almacenado en IndexedDB.
  3. Corrección fonética: El algoritmo Levenshtein mapea palabras del dictado contra el catálogo de productos.
  4. POST al servidor: La PWA envía un JSON vía HTTPS POST al endpoint /api/comanda.php.
  5. Persistencia: PHP valida y ejecuta el procedimiento almacenado RegistrarComanda dentro de una transacción atómica en MariaDB.
  6. TTS Altavoz cocina: El sistema genera audio TTS y lo reproduce por el altavoz conectado a la estación de cocina: "Nueva orden: mesa [N], [productos]."
  7. Notificación diadema cocinero: Si hay comandos pendientes del cocinero (como solicitudes de cancelación), se envían por su diadema.
  8. Respuesta diadema mesero: El sistema confirma el envío por TTS en la diadema del mesero.
  9. Pantalla banner: La nueva comanda aparece en la pantalla de cocina vía SSE o polling.
  10. Comandos del cocinero: El cocinero dicta comandos ("preparar siguiente", "listo mesa cinco") que son procesados por una segunda instancia VOSK con gramática restringida.

2.2.1. Ciclo de Vida General de una Petición HTTP / AJAX

Cuando el usuario interactúa con la WebApp/PWA, las herramientas del lado del cliente y del servidor cooperan de manera síncrona y asíncrona siguiendo esta secuencia exacta:

  1. Disparo e Interceptación (Cliente): El usuario realiza una acción (ej. clic o envío). El motor de HTMX (Vanilla JS) intercepta el evento nativo del navegador, cancela la recarga completa de la página y empaqueta los datos de los formularios de forma asíncrona.
  2. Control de Red e IndexedDB (PWA): Antes de salir del navegador, el evento pasa por el Service Worker Nativo. Si el dispositivo está online, la petición continúa hacia el servidor. Si está offline, el script de cliente usa Dexie.js para almacenar la transacción localmente en la IndexedDB de Chrome, quedando encolada en cola_peticiones_pendientes para su posterior sincronización.
  3. Enrutamiento y Seguridad (Servidor - Apache/Flight): La petición HTTP llega a Apache 2.4 y es despachada por Flight PHP. Lo primero que ejecuta el controlador es la verificación de sesión y permisos a través del objeto PDO centralizado de Delight-PHP/Auth y las reglas del RBAC Personalizado. Si el usuario no tiene permisos, se detiene el flujo y se retorna un fragmento HTML de error.
  4. Procesamiento de Negocio e Idempotencia (Servidor - Medoo/MariaDB): Si el acceso es concedido, el controlador verifica el token de idempotencia en la sesión de PHP para asegurar que no sea un reenvío duplicado. Posteriormente, invoca a Medoo para ejecutar de forma segura la lógica de negocio pesada empaquetada dentro de un Stored Procedure en MariaDB 11.
  5. Renderizado Parcial (Servidor - Plates): Tras recibir los resultados de la base de datos, el controlador pasa las variables al motor de plantillas de Plates. Este genera únicamente el fragmento de HTML modificado (el componente de la vista) junto con bloques de actualización global marcados para intercambio fuera de banda (OOB).
  6. Intercambio de Pantalla y Reactivación (Cliente): HTMX recibe el fragmento HTML del servidor de manera asíncrona. Remueve los indicadores de carga (spinners), vuelve a habilitar los botones y, mediante métodos nativos de Vanilla JS, inyecta el HTML en las zonas de la pantalla indicadas por los atributos de destino (ej. hx-target) sin alterar el resto de la aplicación.

2.2.2. Caso Práctico: Creación de Pedido por Dictado de Voz Inteligente

Este escenario describe el flujo de datos exacto cuando un usuario con rol de "Mesero" o "Operario" presiona un botón, dicta un comando de voz (ej: "Registrar pedido de 50 unidades" o comanda de productos), el sistema lo procesa con Inteligencia Artificial, guarda la información en la base de datos de forma segura y actualiza la pantalla junto con las notificaciones push.

  • Fase 1: Interacción Inicial en el Navegador: El operario carga la interfaz generada originalmente por el motor de vistas Plates. Presiona el botón de micrófono. Un script de Vanilla JS activa la API nativa de audio de Chrome para capturar los fragmentos binarios de voz del operario.
  • Fase 2: Procesamiento Concurrente de IA en el Servidor (IT2): El script de cliente transmite el flujo de audio asíncronamente abriendo un canal persistente hacia el servidor independiente de Swoole (en el puerto 6003). Swoole recibe los datos binarios de red y abre una conexión directa por sockets de alta velocidad hacia el contenedor aislado de alphacep/kaldi-es (Vosk). La IA de Vosk procesa el audio localmente y le devuelve a Swoole el texto plano transcribido: "Registrar pedido de 50 unidades". Swoole envía el texto de vuelta al navegador a través del mismo WebSocket.
  • Fase 3: Ejecución Transaccional en el Backend: Al recibir el texto transcribido, HTMX entra en acción automáticamente simulando un envío seguro de formulario enviando un POST hacia la ruta de control /pedidos/crear administrada por Flight PHP. El formulario de HTMX adjunta un token de idempotencia único e invisible. Flight PHP recibe la petición e invoca a Delight-PHP/Auth junto con las tablas de permisos del RBAC personalizado para cerciorarse de que el usuario logueado posee el permiso de escritura CREAR_PEDIDOS. Validada la seguridad, el controlador invoca a Medoo, el cual ejecuta un Stored Procedure en MariaDB 11 que inserta el pedido, actualiza los inventarios y confirma la transacción de forma aislada y segura.
  • Fase 4: Respuesta de Interfaz y Notificación Push: Tras el éxito en MariaDB, Flight PHP le solicita a Plates renderizar solo el fragmento de la nueva fila de la tabla de pedidos. Al final del archivo de Plates, se incluye un bloque HTML con el atributo hx-swap-oob="true" conteniendo las nuevas migas de pan actualizadas (Inicio / Pedidos / Creado Exitosamente). HTMX recibe la respuesta asíncrona, inyecta la nueva fila en la tabla de pedidos, actualiza los breadcrumbs externos y apaga el indicador visual de carga (spinner). Paralelamente, el servidor envía un evento push global. El Service Worker Nativo del navegador despierta en segundo plano y muestra una notificación nativa en la pantalla del usuario confirmando el registro del pedido.

3.3. Filosofía de Frugalidad del Stack

El diseño del sistema de comandas se rige por un principio estricto de frugalidad técnica y rechazo a frameworks pesados (como React, Angular o Laravel) para optimizar el rendimiento en el hardware local limitado (Servidor y teléfonos de gama media/baja). Se prioriza el intercambio de hipermedia servidor-cliente y el uso de librerías nativas o de bajo peso que no exigen procesos de compilación o empaquetado (build steps) costosos:

  • Minimización de JS en Cliente: Todo el dinamismo de la UI se delega a HTMX, reduciendo el código JS a la gestión de hardware (micrófono, audio) y sincronización (app.js, Web Worker de Vosk).
  • Ejecución Server-Side Eficiente: Flight PHP es un micro-framework de ultra-bajo consumo de memoria (~2MB de RAM por request) comparado con frameworks empresariales que cargan cientos de clases innecesarias en cada petición.
  • Persistencia Liviana: MariaDB y Medoo reemplazan los ORM acoplados y lentos (como Doctrine o Eloquent). Toda la lógica transaccional compleja se desplaza a Stored Procedures optimizados directamente en la base de datos, resolviendo peticiones críticas en tiempo submilisegundo.

3.4. Configuración de HTMX en el Ecosistema Ligero

La adopción de HTMX permite construir una SPA (Single Page Application) ligera manteniendo el control del estado y del HTML en el servidor (Flight/Plates). Las directivas de integración clave son:

  • hx-boost: Habilitado globalmente para interceptar todas las etiquetas <a> y formularios de la aplicación, convirtiendo las recargas tradicionales en llamadas AJAX transparentes.
  • Intercambios Fuera de Banda (OOB): Utilizado activamente (hx-swap-oob="true") para actualizar elementos de interfaz remotos (ej. barra de estado del mesero, breadcrumbs, totales del día) en una única respuesta HTTP, sin necesidad de realizar múltiples peticiones AJAX paralelas.
  • Control de Retroalimentación de UI: Se configuran las clases .htmx-request y hx-indicator para activar automáticamente spinners e indicadores de carga globales, previniendo la frustración del usuario en llamadas lentas.

3.5. Estrategia de Persistencia y Criterios de Uso de Medoo

Medoo se utiliza como el constructor de consultas (Query Builder) centralizado para la comunicación con MariaDB 11, proveyendo inmunidad nativa a ataques de Inyección SQL mediante sentencias parametrizadas basadas en PDO:

  • Transiciones Estructurales: Toda consulta que altere el estado financiero o de comandas debe usar la abstracción de transacciones de Medoo: 
    $db->action(function($db) {
    // Lógica secuencial
});
  • Invocación de Procedimientos Almacenados: Medoo no realiza mapeo relacional de objetos complejo. En su lugar, actúa como un puente directo para invocar Stored Procedures optimizados de base de datos: 
    $db->query("CALL RegistrarComanda(:params)", $params);

4.2. Procedimientos Almacenados

RegistrarComanda

DELIMITER //
CREATE PROCEDURE RegistrarComanda(
    IN p_mesa_id INT,
    IN p_mesero_id INT,
    IN p_texto_transcrito TEXT,
    IN p_json_productos JSON
)
BEGIN
    DECLARE v_comanda_id INT;
    DECLARE v_total DECIMAL(10,2) DEFAULT 0.00;
    DECLARE v_producto_id INT;
    DECLARE v_cantidad INT;
    DECLARE v_precio DECIMAL(10,2);
    DECLARE i INT DEFAULT 0;
    DECLARE n INT;
    START TRANSACTION;
    INSERT INTO comandas (mesa_id, mesero_id, texto_transcrito, total)
    VALUES (p_mesa_id, p_mesero_id, p_texto_transcrito, 0.00);
    SET v_comanda_id = LAST_INSERT_ID();
    SET n = JSON_LENGTH(p_json_productos);
    WHILE i < n DO
        SET v_producto_id = JSON_UNQUOTE(JSON_EXTRACT(p_json_productos,
            CONCAT('$[',i,'].producto_id')));
        SET v_cantidad = JSON_UNQUOTE(JSON_EXTRACT(p_json_productos,
            CONCAT('$[',i,'].cantidad')));
        SELECT precio INTO v_precio FROM productos WHERE id = v_producto_id AND disponible = 1;

                precio_unitario, subtotal)

            SET v_total = v_total + (v_precio * v_cantidad);
        END IF;
        SET i = i + 1;
    END WHILE;
    UPDATE comandas SET total = v_total WHERE id = v_comanda_id;
    COMMIT;
    SELECT v_comanda_id AS comanda_id, v_total AS total, 'success' AS estado;

6. Arquitectura de Reconocimiento de Voz (STT)

El sistema implementa dos arquitecturas independientes de dictado de voz a texto (STT), denominadas "Prioridades". Ambas arquitecturas cubren íntegramente las funcionalidades y flujos de negocio para todos los actores (Meseros y Cocineros), y la única diferencia radica en la ubicación física donde ocurre la inferencia de Inteligencia Artificial (Cliente vs. Servidor) y el medio de transmisión subyacente.

6.1. Prioridad 1: VOSK Frontend (Arquitectura Cliente-Servidor Ligera)

Estrategia IT1: Procesamiento Local en el Cliente (PWA)

En esta versión, tanto la PWA del Mesero como la WebApp de la Cocina descargan y ejecutan Vosk JS localmente en el navegador asistidos por Web Workers. El audio nunca viaja por la red. El canal de transmisión se limita a enviar el texto ya transcrito hacia el backend vía HTTP/AJAX o WebSockets ligeros.

Flujo de Trabajo y Pipeline (IT1 - Frontend)

  1. Captura Local: El AudioWorkletNode del navegador captura el micrófono a 16 kHz, PCM mono.
  2. Decodificación WASM: Los fragmentos PCM se envían al Web Worker local nativo donde el modelo acústico de VOSK genera la transcripción a texto.
  3. Corrección y Limpieza: El script del cliente (PWA) aplica la corrección fonética (Levenshtein) basándose en el catálogo local de productos o comandos.
  4. Sincronización (Offline-First): El texto limpio se transmite. Si se pierde la red (común en meseros en movimiento), el texto se encola en IndexedDB (tabla offline_text_queue) y se sincroniza automáticamente al recuperar la señal.
// Ejemplo Pipeline IT1 (Aplica a Meseros y Cocineros)
const stream = await navigator.mediaDevices.getUserMedia(constraints);
const audioContext = new AudioContext({ sampleRate: 16000 });
await audioContext.audioWorklet.addModule('js/audio-processor.js');
const workletNode = new AudioWorkletNode(audioContext, 'pcm-processor');

workletNode.port.onmessage = (e) => {
    const pcmBuffer = e.data;
    if (recognizer.acceptWaveform(pcmBuffer)) {
        const result = recognizer.result();
        procesarTextoYEnviar(result.text); // Enviar texto limpio al servidor
    }
};

6.2. Prioridad 2: VOSK Backend (Arquitectura de Streaming)

Estrategia IT2: Procesamiento Centralizado en el Servidor

En esta versión, los navegadores (PWA Mesero y KDS Cocina) actúan únicamente como micrófonos tontos, delegando la carga computacional pesada al servidor. El canal de comunicación se vuelve un túnel intensivo de Audio Streaming. Permite utilizar modelos acústicos hiper-precisos, pero requiere conectividad ininterrumpida a la red local.

Flujo de Trabajo y Pipeline (IT2 - Backend)

  1. Captura y Streaming: El navegador graba la voz y la empaqueta intermitentemente en fragmentos binarios (Audio Blobs).
  2. Túnel WebSocket: Los blobs se transmiten en tiempo real por un canal WebSocket hacia el servidor Swoole (Puerto 6003).
  3. Decodificación Docker: Swoole recibe los paquetes binarios y los redirige internamente al contenedor local alphacep/kaldi-es (Vosk).
  4. Retorno y Ejecución: El servidor Swoole obtiene el texto, invoca la API interna de PHP para registrar la comanda o el estado, y envía la respuesta final (confirmaciones JSON y directivas TTS) de vuelta al navegador por el mismo WebSocket.

function sintetizarVoz(texto, callback = null) {
    const utterance = new SpeechSynthesisUtterance(texto);
    utterance.lang = 'es-MX';
    utterance.rate = 1.1;
    utterance.pitch = 1.0;

7.2. Cola de Mensajes TTS

Para evitar solapamiento de mensajes, se implementa una cola FIFO de reproducción:

class ColaTTS {
    constructor() {
        this.cola = [];
        this.reproduciendo = false;
    }

    encolar(texto) {
        this.cola.push(texto);
        if (!this.reproduciendo) this.procesar();
    }

    procesar() {
        if (this.cola.length === 0) {
            this.reproduciendo = false;
            return;
        }
        this.reproduciendo = true;
        const texto = this.cola.shift();
        sintetizarVoz(texto, () => this.procesar());
    }
}

7.4. Prevención de la "Voz Fantasma" (TTS Desfasado)

Riesgo Crítico de UX y Ruido Acústico

Si múltiples notificaciones push de comandas se encolan debido a una desconexión temporal de la red Wi-Fi y luego la conexión se restablece bruscamente, la API SpeechSynthesis nativa del navegador intentará reproducir secuencialmente todas las alertas viejas acumuladas, saturando el canal de audio del mesero o cocinero con información obsoleta ("Voz Fantasma").

Estrategia de Mitigación en app.js:

  • Cada notificación push o comando recibido por el cliente incluye obligatoriamente la marca de tiempo de envío original del servidor (server_sent_timestamp).
  • Antes de encolar un mensaje en la ColaTTS local, el script valida si la diferencia de tiempo entre el reloj del cliente y el servidor supera un umbral de 5 segundos.
  • Si el mensaje supera el límite, se cancela la síntesis de voz mediante window.speechSynthesis.cancel() y se descarta auditivamente el mensaje, actualizando la interfaz visual en un panel histórico silencioso de manera que el operario solo escuche notificaciones relevantes para el instante actual.

8.3. Patrones de Interacción y UX (Buenas Prácticas)

Para garantizar una navegación fluida e impedir la pérdida de datos transaccionales, el frontend de la PWA implementa las siguientes directivas de experiencia de usuario:

  • Idempotencia en UI (hx-disabled-elt): Para evitar clics duplicados rápidos que generen órdenes redundantes en la base de datos, se delega el control de los elementos interactivos a HTMX. Mediante el atributo hx-disabled-elt="this, #btn-enviar", HTMX deshabilita automáticamente los botones seleccionados durante la llamada AJAX y los reactiva al recibir la respuesta del servidor.
  • Patrón PRG (Post-Redirect-Get): Los flujos de escritura (como el envío de una orden) evitan que refrescos accidentales de pantalla dupliquen transacciones. En peticiones asíncronas, Flight PHP responde con la cabecera HX-Redirect en lugar de redireccionamientos HTTP tradicionales. Adicionalmente, se adjunta un token de un solo uso en cada formulario que el servidor invalida tras su procesamiento inicial.
  • Bloqueo de Interfaz (Overlay Spinner): Se implementa una capa superior global (Overlay) controlada automáticamente por HTMX mediante la clase .htmx-request vinculada a hx-indicator, bloqueando la pantalla durante transacciones lentas para evitar interacciones no deseadas del mesero.
  • Manejo de Breadcrumbs (Migas de Pan): Debido al intercambio parcial de HTML, los breadcrumbs y la barra superior se actualizan mediante Intercambios Fuera de Banda (OOB) marcados con hx-swap-oob="true", permitiendo mantener la navegación sincronizada de forma eficiente.

8.4. Especificación y Diseño Lógico de app.js

El archivo app.js centraliza la gestión del hardware de audio, el Web Worker de Vosk y el almacenamiento transaccional local en IndexedDB:

1. Gestión de Persistencia Local (Dexie.js / IndexedDB)

Al arrancar, app.js inicializa las tablas locales con Dexie.js para contingencias offline y notificaciones:

  • offline_text_queue: Cola FIFO para almacenar transcripciones limpias (Estrategia IT1) generadas en desconexión.
  • offline_audio_queue: Cola FIFO de blobs de audio PCM crudo (Estrategia IT2) pendientes de envío al WebSocket de Swoole.
  • buzon_notificaciones: Almacén local que retiene las últimas 20 notificaciones push (eventos de cocina), garantizando que el historial sobreviva a recargas del navegador. La actualización del DOM se inyecta posteriormente de manera reactiva usando HTMX y la API nativa de IndexedDB.

2. Control de Captura de Audio e Hilos de Micrófono

Se maneja la API nativa de audio de Chrome (AudioContext y MediaRecorder) aislando el procesamiento:

  • La captura se fuerza a 16 kHz monofónico (16-bit PCM) según requerimientos del motor VOSK.
  • En IT1, alimenta un canal continuo hacia el Web Worker. En IT2, empaqueta el audio en Audio Blobs (PCM/WAV) de corta duración para transmisión secuencial por WebSockets.

3. Orquestación del Reconocedor Vosk JS en Cliente (Web Workers)

Dado el alto consumo de CPU de la IA local, app.js ejecuta el motor Vosk en un hilo secundario (Web Worker nativo):

  • La mensajería se realiza mediante postMessage() y el escucha onmessage para recibir resultados de transcripción sin congelar el hilo principal de renderizado visual de la PWA.

4. Flujo de Sincronización y Recuperación de Red

Al detectar la restauración de red (navigator.onLine === true):

  • Para IT1: Lee secuencialmente la cola de textos y los envía a Flight PHP vía Fetch/AJAX.
  • Para IT2: Extrae los blobs de audio de IndexedDB, reabre el WebSocket de Swoole y transmite la cola.
  • Una vez confirmada la persistencia por el servidor, limpia físicamente los registros de la IndexedDB para evitar el desbordamiento del almacenamiento local del dispositivo Android.

11.2. Resiliencia Operativa

  • Reconocimiento 100% offline: VOSK no requiere internet. La transcripción ocurre localmente.
  • Cola offline: Comandas se almacenan en IndexedDB ante pérdida de Wi-Fi y se sincronizan al restaurar.
  • Independencia de cloud: Sin dependencia de AWS, Google Cloud, Azure, ni APIs externas.
  • UPS recomendado: 600VA+ para protección ante cortes eléctricos.
  • Caché persistente: El modelo VOSK permanece en IndexedDB tras reinicios del navegador.
  • Evicción IndexedDB: Llamar a navigator.storage.persist() para solicitar almacenamiento persistente y evitar que el navegador elimine el modelo VOSK o la cola offline.
  • Dexie en modo incógnito: IndexedDB puede fallar silenciosamente en modo incógnito. Envolver operaciones Dexie en try/catch y avisar al usuario si la persistencia no está disponible.
  • Background Sync en Doze Mode (D1): En Android con ahorro de batería activo, el Service Worker puede estar congelado horas. Las comandas offline no se envían automáticamente al reconectar. Solución: cola de reintentos manual en Dexie como respaldo.

11.3. Privacidad

  • Audio nunca sale del dispositivo: Las grabaciones se procesan localmente y no se transmiten ni almacenan.
  • Datos almacenados mínimos: Solo texto transcrito, hora y productos. Sin biométricos ni datos sensibles de clientes.
  • Control local: Todos los datos residen físicamente en el servidor del restaurante.

11.5. Control Cronológico y Mitigación de Desfases (Marcas de Tiempo)

En un entorno offline, la desincronización de relojes entre los dispositivos cliente (Chrome) y el servidor (Apache/MariaDB) o el envío de comandas horas después de su creación debido a fallas de red, exige políticas cronológicas estrictas:

1. Flujo PWA hacia Servidor (PWA to Server Side)

  • Al finalizar un dictado o acción en la PWA, el script app.js inyecta en el payload de IndexedDB:
    • cliente_timestamp: La hora absoluta del dispositivo (para auditoría).
    • duracion_offline_ms: Un contador dinámico que inicia en 0 y acumula la duración exacta que el registro pasa encolado localmente.
  • Al restaurar la conexión, el Service Worker transmite el payload con el valor acumulado de duracion_offline_ms.
  • El servidor calcula el instante real del registro restando el tiempo offline del instante de recepción: 
    Hora_Real_Registro = server_received_time - duracion_offline_ms
  • Esta marca calculada se inyecta en los Stored Procedures de MariaDB, garantizando que el historial refleje la secuencia cronológica real del negocio, independientemente de desfases de red.

2. Flujo Servidor hacia PWA (Server Side to PWA)

  • Las alertas y notificaciones emitidas por Swoole o Server-Sent Events (SSE) incluyen obligatoriamente server_sent_timestamp y un tiempo de vida útil (ttl_segundos, ej: 120s).
  • Si al llegar al cliente la diferencia temporal excede el TTL, la alerta se descarta o desvía a un historial secundario silencioso.
  • Para evitar que ráfagas de notificaciones acumuladas durante desconexiones activen la reproducción masiva de TTS ("Voz Fantasma"), el script limpia la cola de SpeechSynthesis ejecutando window.speechSynthesis.cancel() si el desfase del paquete entrante excede los 5 segundos.

11.6. Conflicto de Entornos de Ejecución: Apache/Flight vs. Swoole

El backend del sistema coexiste bajo dos modelos de ejecución con filosofías incompatibles:

  • Apache + Flight PHP: Opera bajo el ciclo de vida clásico de PHP (petición entrante, carga de bootstrap, renderizado con Plates y destrucción de memoria). Ideal para la lógica de negocio, REST API y CRUD tradicionales.
  • Swoole CLI Server: Servidor asíncrono y persistente en memoria. Bloquea el proceso y no utiliza las variables superglobales clásicas ($_SERVER, $_SESSION). Diseñado para la transmisión bidireccional en tiempo real de WebSockets y el túnel de comunicación rápida con Vosk (Estrategia IT2).

Resolución de Coexistencia:

Se divide la arquitectura física en dos servicios autónomos e independientes:

  1. El 95% de la aplicación (vistas Plates, rutas HTTP ordinarias de comanda/caja) corre sobre el Apache tradicional administrado por Flight PHP en los puertos estándar (80/443).
  2. El servidor Swoole se inicia como un demonio CLI en un puerto aislado (puerto 6003), actuando exclusivamente como un microservicio WebSocket encargado de canalizar el streaming binario de audio de IT2 y el puente socket directo al contenedor Vosk.

VOSK
Toolkit de reconocimiento de voz offline de código abierto basado en Kaldi. Ejecuta localmente en el navegador vía WebAssembly o centralizado en el servidor mediante contenedores Docker.

Formato binario ejecutable en navegadores a velocidad cercana al código nativo. Permite ejecutar el modelo acústico de VOSK en el dispositivo del mesero usando los procesadores locales, sin instalar librerías adicionales.
IndexedDB / Dexie.js
Base de datos transaccional integrada en el navegador, utilizada mediante el wrapper Dexie.js para almacenar la cola offline de comandas (IT1/IT2) y el buzón histórico de notificaciones Push PWA.
AudioWorklet
API de procesamiento de audio nativa de baja latencia que opera en un hilo secundario y captura el micrófono en un buffer circular a 16 kHz PCM mono, previniendo cuellos de botella en la interfaz de usuario.

Tecnología de comunicación unidireccional (Servidor a Cliente) de bajo consumo, ideal para inyectar actualizaciones de estado de órdenes en la pantalla Banner del KDS de cocina sin forzar conexiones bidireccionales pesadas.
Swoole Async Server
Extensión de PHP que convierte la ejecución en un servidor asíncrono y manejador de WebSockets (Puerto 6003), utilizado para transmitir streams continuos de audio crudo (PCM) en tiempo real para la estrategia IT2.
