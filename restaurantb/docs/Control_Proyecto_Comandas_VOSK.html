1. Registro de Implementación (Hechos / Dones)

1.1. Desarrollo e Infraestructura Base

  • Creación Automatizada de la Base de Datos: Se desarrolló un script orquestador en Bash (setup.sh) que extrae de manera dinámica las credenciales del entorno MCP y aprovisiona la base de datos vcd01 junto con los usuarios transaccionales y datos semilla.
  • Unificación de Autenticación (Delight-Auth): Se crearon y conectaron las tablas maestras de seguridad de Delight-PHP (users, users_remembered, users_throttling, users_audit_log, users_2fa, users_confirmations, users_resets) de manera independiente a las tablas operativas (empleados).
  • Procedimientos Almacenados Seguros: Implementación de RegistrarComanda y CerrarCuentaMesa para encapsular la lógica transaccional y el cálculo dinámico de subtotales a nivel de motor de datos.
  • Optimización (Índices SQL): Se incluyó un script dedicado (06_indexes.sql) para la creación de índices BTREE sobre las columnas estado y hora_captura de las comandas, optimizando el renderizado del KDS de cocina y los cierres de mesa.
  • Generación de Activos PWA (Dexie.js): Se estructuró físicamente el almacenamiento local (Offline-First) descargando dexie.min.js para acceso LAN, y desarrollando el módulo db.js (Definición de ComandasDB) y sw.js (Service Worker para interceptar eventos Background Sync). Todo dentro del directorio web-assets/ accesible localmente.

1.2. Hitos de Infraestructura de Red Local (HTTPS y Micrófono)

1.6. Motor de Versionado de Datasets y Simulación NLP (Julio 2026)

  • Esquema catalogo_versiones: Creación de la tabla catalogo_versiones para almacenar instantáneas (snapshots) JSON del catálogo de productos con sus respectivas palabras clave, el mapa de sinónimos de cantidad y los umbrales configurables de Levenshtein. Sincronizado en el pipeline general de base de datos a través de setup.sh.
  • Panel de Edición Interactiva de Palabras Clave: Desarrollo del panel web de administración con diseño Glassmorphism que permite al gerente editar las palabras clave de búsqueda fonética para cada producto directamente desde una cuadrícula tabular (e.g. agregar variaciones locales, sinónimos como "pastor", "trompo", "refresco", "coca de 600", etc.).

Permite probar la transcripción del mesero usando el estado en caliente de los inputs del catálogo (sin guardar ni publicar previamente), mostrando el análisis morfológico de mesa, cantidades interpretadas vía sinónimos, notas ("sin cebolla", "con queso") y el cálculo detallado de distancia de Levenshtein contra palabras clave.
  • Versionado e Invalidation local por Delta Hash: Flujo donde cada guardado genera un hash MD5 de la configuración para validación delta. Al publicar una versión, el backend cambia el flag activo y notifica a los dispositivos PWA al momento de su inicio de sesión o restablecimiento de conexión para invalidar el caché local e inicializar KaldiRecognizer con el nuevo conjunto de gramática.

1.13. Corrección del Error 500, Redirecciones y Permisos Docker (Julio 2026)

  • Mapeo Seguro del Singleton de Base de Datos: Se eliminó Flight::register('db', 'PDO'), que disparaba una excepción PHP al intentar instanciar PDO sin argumentos, y se reemplazó con el mapeo seguro del singleton mediante Flight::map('db', ...) resolviendo el error 500.
  • Alineación de Redirecciones en Flight PHP: Se removió el prefijo /restaurant hardcodeado en las redirecciones del framework (por ejemplo, en el archivo index.php y RbacManager.php). Dado que Flight auto-detecta la URL base, prefijar el contexto producía bucles de redirección hacia rutas duplicadas (ej: /restaurant/restaurant/login) derivando en errores 404.
  • Entrypoint Auto-Reparable para Logs en Docker: Para solventar de forma definitiva y reproducible los problemas de permisos de escritura (error 500 de logs) en el volumen mapeado, se inyectó en docker-entrypoint-ssl.sh la creación dinámica y asignación de permisos máximos (chmod 777) al directorio de logs antes de iniciar Apache, acompañado de un archivo placeholder .gitkeep para asegurar su seguimiento bajo control de versiones.
  • Guía Rápida de Despliegue e Instalación: Se generó un nuevo documento especializado en la suite (Instrucciones_Despliegue_Comandas_VOSK.html) detallando paso a paso el flujo de lanzamiento con Docker Compose, inyección de certificados HTTPS locales y el estándar estricto de activos estáticos web-assets absolutos en las vistas PHP.

2. Issues Conocidos y Mitigaciones

2.1. PWA Android y Hardware

Issues y GAPs de PWA Android
IDIssueImpactoMitigación
A3AudioContext suspendido por política de autoplayChrome Android suspende el AudioContext si no hubo gesto del usuario primero. VOSK no recibe audio aunque el micrófono esté aceptado.audioContext.resume() dentro del onclick del botón de voz.
GAP-1Permiso de micrófono en AndroidManifest.xmlEn el AndroidManifest.xml que genera Bubblewrap hay que agregar RECORD_AUDIO y MODIFY_AUDIO_SETTINGS. Sin esto, getUserMedia() puede fallar silenciosamente dentro del APK.Declarar permisos en el manifest antes de generar el APK.
GAP-2Digital Asset Links (TWA)Si assetlinks.json no está correctamente configurado en /.well-known/, el APK se abre como Custom Tab con barra de URL visible en lugar de pantalla completa como TWA.Configurar assetlinks.json en el servidor web con el fingerprint SHA-256 del APK.
COOPSharedArrayBuffer para VOSK WASM (COOP/COEP)VOSK WASM requiere SharedArrayBuffer, que necesita Cross-Origin Isolation.✅ Resuelto: Se inyectan Cross-Origin-Embedder-Policy: credentialless y same-origin en index.php de Flight.
HTTPSHTTPS obligatorio para getUserMediagetUserMedia() está bloqueado en HTTP plano, sin excepción.Certificado firmado por mkcert (CA local) instalado en el dispositivo cliente. (Resuelto, ver sección de Dones).
PERMPermiso runtime (diálogo de usuario)Una vez declarado en el manifest, Android muestra el diálogo al usuario la primera vez que VOSK llama getUserMedia().Funciona igual en PWA browser y en TWA APK. No requiere acción adicional.
D1Background Sync no dispara en Doze ModeService Worker congelado horas con ahorro de batería activo. Comandas offline no se envían al reconectar.Cola de reintentos manual en Dexie como respaldo independiente de Background Sync.
E1Android 16 fuerza layout adaptativo en tabletasDesde Android 16 (API 36), soporte de todas las orientaciones y aspect ratios es obligatorio para pantallas ≥600dp. Google Play lo requiere desde agosto 2026.✅ Resuelto: orientation: any en manifest.json inyectado.

EVICTEvicción IndexedDBEl navegador puede eliminar datos de IndexedDB bajo presión de almacenamiento.✅ Resuelto: navigator.storage.persist() solicitado asíncronamente en app-main.js.
SW-1Service Worker no activo en primera cargaEl SW no intercepta requests hasta la segunda visita.✅ Resuelto: skipWaiting() + clients.claim() implementado en el Service Worker.
TTS-BLKTTS interrumpida al bloquear pantallaLa síntesis de voz se detiene si el dispositivo se bloquea o la pantalla se apaga.✅ Resuelto: navigator.wakeLock.request('screen') invocado en cocina-voice.js.

GAP-3Integridad del modelo VOSK offlineDescargas incompletas del modelo VOSK (~39MB) por red inestable causan corrupción persistente en IndexedDB.Detección y reintento automático de descarga / reinstalación si falla la inicialización de VOSK.
GAP-4Bloqueo de UI por carga de WASMCompilar el modelo WASM de VOSK en el hilo principal bloquea y congela la UI del mesero.✅ Resuelto: Delegación obligatoria del reconocedor VOSK al Web Worker secundario (vosk-worker.js).
GAP-5Paridad de catálogo y desfase de versionesComandas enviadas offline pueden contener productos descontinuados si el catálogo cambió en el servidor.Sincronización de catálogo con Delta Hash check previo al inicio del turno para invalidación local.

3.6. Prioridad de Desarrollo #4: Fase 5 - Pantallas e Impresión Térmica (Red Local)

Fase de Pantallas y Salida Física (Tickets)

Habilitar la visualización del KDS secundario (Banner de Cocina) y la integración de tickets de cobro impresos por hardware en la red local (LAN).

  • ToDo 1 (Pantalla Banner Cocina): Crear una vista informativa gigante para cocina que agrupe y muestre de manera consolidada los totales acumulados a preparar (ej. "10 Tacos Pastor, 5 Gringas") para evitar que el cocinero tenga que leer comanda por comanda.
  • ToDo 2 (Módulo de Impresión Local - CUPS): Diseñar e implementar el script de backend conectado al servidor de impresión local (CUPS en red local) para imprimir tickets de cobro y comandas físicamente al realizar el cierre de mesa.
  • ToDo 3 (Pantalla de Caja / Checkout): Refinar la interfaz web del Cajero para el cobro manual e impresión física de tickets, con soporte para pagos en efectivo/tarjeta y cálculo de cambio.

3.7. Prioridad de Desarrollo #5: Fase 6 - Carga de Catálogo y Configuración de Diademas

Fase de Configuración de Datos y Operación de Voz

Afinar el catálogo oficial de productos con sus sinónimos fonéticos y configurar los dispositivos físicos para la operación.

  • ToDo 1 (Carga de Catálogo Oficial): Importar la lista real de productos del menú de la taquería y asignar sus palabras clave iniciales en la base de datos (Delta Hash).
  • ToDo 2 (Configuración de Diademas de Voz): Pruebas y calibración de los auriculares / diademas Bluetooth y de cable en las tablets de los meseros y cocineros para calibrar la cancelación de ruido y el volumen de síntesis de voz (TTS).
