Este documento consolida toda la documentación, infraestructura y arquitectura de la estrategia "IT2", la cual fue descartada en favor de una arquitectura 100% cliente (Offline-First VOSK WASM) para reducir la complejidad técnica y estabilizar el sistema. Se mantiene como referencia histórica.

1. Concepto Arquitectónico (IT2)

Procesamiento Concurrente de IA en el Servidor (IT2): El script de cliente transmite el flujo de audio asíncronamente abriendo un canal persistente hacia el servidor independiente de Swoole (en el puerto 6003). Swoole recibe los datos binarios de red y abre una conexión directa por sockets de alta velocidad hacia el contenedor aislado de alphacep/kaldi-es (Vosk). La IA de Vosk procesa el audio localmente y le devuelve a Swoole el texto plano transcribido: "Registrar pedido de 50 unidades". Swoole envía el texto de vuelta al navegador a través del mismo WebSocket.

  • En IT2, se empaqueta el audio en Audio Blobs (PCM/WAV) de corta duración para transmisión secuencial por WebSockets.
  • Para la cola offline de IT2: Extrae los blobs de audio de IndexedDB, reabre el WebSocket de Swoole y transmite la cola.

2. Flujo de Trabajo y Pipeline (Backend Swoole + Docker)

// Ejemplo Pipeline IT2 (Aplica a Meseros y Cocineros)
// 1. Navegador captura audio mediante getUserMedia
// 2. Audio se convierte a PCM Blobs (ej. cada 250ms)
// 3. Blobs se transmiten vía ws://192.168.1.71:6003 (Swoole)
// 4. Swoole actúa como proxy passthrough a ws://127.0.0.1:2700 (Kaldi Docker)
// 5. Kaldi realiza Inferencia HCLG con gramática amplia
// 6. Swoole devuelve JSON al navegador
// 7. Navegador aplica Levenshtein contra el catálogo

4. Conflicto de Entornos de Ejecución: Apache/Flight vs. Swoole

El backend del sistema bajo IT2 coexistía bajo dos modelos de ejecución con filosofías incompatibles:

  • Apache + Flight PHP: Opera bajo el ciclo de vida clásico de PHP (petición entrante, carga de bootstrap, renderizado con Plates y destrucción de memoria). Ideal para la lógica de negocio, REST API y CRUD tradicionales.
  • Swoole CLI Server: Servidor asíncrono y persistente en memoria. Bloquea el proceso y no utiliza las variables superglobales clásicas ($_SERVER, $_SESSION). Diseñado para la transmisión bidireccional en tiempo real de WebSockets y el túnel de comunicación rápida con Vosk (Estrategia IT2).

Resolución de Coexistencia (Histórica):

  1. El 95% de la aplicación (vistas Plates, rutas HTTP ordinarias de comanda/caja) corría sobre el Apache tradicional administrado por Flight PHP en los puertos estándar (80/443).
  2. El servidor Swoole se iniciaba como un demonio CLI en un puerto aislado (puerto 6003), actuando exclusivamente como un microservicio WebSocket encargado de canalizar el streaming binario de audio de IT2 y el puente socket directo al contenedor Vosk.
