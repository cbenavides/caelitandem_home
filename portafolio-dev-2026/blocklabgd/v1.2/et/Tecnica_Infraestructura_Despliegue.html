11.2. Optimización WPO del Portal Web Estático (OCI / .htaccess)

⚠️ Nota de alcance: El .htaccess aplica exclusivamente al despliegue estático en OCI (n8n-php/mvps/laesh-ui/uipv1/.htaccess) donde Nginx actúa como proxy a Apache. En el stack Docker local (LNMP: Nginx + PHP-FPM), no existe .htaccess: las directivas de caché, GZIP y cabeceras de seguridad se declaran directamente en restaurantb.conf (bloques location Nginx). El router PHP (Flight) atiende /laesh/, /laesh/md, /laesh/rc, /laesh/adrc sin Apache.

Se implementaron directivas de seguridad y optimización de transferencia (WPO) mediante la creación de un archivo .htaccess en la raíz del sitio web estático de OCI (uipv1/.htaccess):

  • Compresión GZIP (mod_deflate): Habilitada para comprimir al vuelo recursos de texto plano (HTML, CSS, JS, SVG, JSON) antes de su transporte de red.
  • Políticas de Expiración de Caché (mod_expires):
    • Caché agresiva de 1 año para imágenes (formatos WebP, JPEG, PNG, SVG) y fuentes web, reduciendo el consumo de ancho de banda a 0 bytes en visitas subsecuentes.
    • Caché moderada de 1 mes para hojas de estilo estáticas (CSS) y archivos de lógica UI (JavaScript).
    • Sin caché (0 segundos) para el documento HTML, forzando al navegador a solicitar de forma síncrona el contenido dinámico del CMS en cada visita.

11.3. Radiografía de la Optimización Lograda (WPO)

La auditoría y ejecución de optimización sobre los recursos del portal arrojó métricas de rendimiento sobresalientes en la red local y simulación de producción:

  • Reducción de Peso de Recursos (Ahorro del 98%):
    • Peso Original (JPEG/PNG Raw): Superior a 70 Megabytes, lo cual hacía inviable la carga en conexiones móviles 3G/4G.
    • Peso Optimizado (WebP): Convertidos todos los activos a WebP (calidad 80%) y redimensionados (Hero a 1920px de ancho, secciones/áreas a 1000px). El peso total del directorio de imágenes se redujo a tan solo 1.5 Megabytes.
  • Optimización del Render Loop (LCP y Conectividad):
    • Preload del LCP: La imagen crítica del primer slide (RECEPCION.webp) se pre-carga de manera prioritaria vía la cabecera <link rel="preload"> para acelerar el renderizado visual inicial (Largest Contentful Paint).
    • Diferimiento de Red (Lazy Loading): Aplicación nativa de loading="lazy" y decoding="async" a las 48 imágenes y recursos vectoriales de secciones secundarias.
    • Diferimiento de Iframe (Google Maps): Se bloquea la descarga de scripts de Google Maps al inicio (evitando descargar ~600 KB innecesarios) usando data-src en el iframe. La carga ocurre dinámicamente solo si el usuario selecciona explícitamente la pestaña "Mapa Interactivo".
    • Pre-conexión de Servidores (Preconnect): Inyección de directivas preconnect para acelerar en 150-200ms el establecimiento de socket TLS con los servidores CDN de Google Fonts.

13.8. Estrategia y Arquitectura de Fallbacks (Tolerancia a Fallos Web)

Para garantizar una alta usabilidad y disponibilidad en navegadores web (Desktop, Tabletas e iOS/Android) sin depender de arquitecturas de aplicaciones instalables (PWA/Apps), el proyecto implementa un sistema unificado de 5 niveles de fallbacks:

Tabla. Matriz de Fallbacks y Resiliencia en Frontend
#Nivel / CategoríaMecanismo / ImplementaciónUbicación en CódigoPropósito y Comportamiento
F-1 Accesibilidad y No-JS Etiqueta <noscript> con enlace alternativo directo a Google Maps uipv1/index.html (L. 1070) Si el usuario desactiva JavaScript o este falla en ejecutarse, en lugar del mapa interactivo bloqueado se despliega un hipervínculo plano seguro y accesible hacia la ubicación en Google Maps.

15.6. PHP — Manejo Explícito Error 1969 (DB.php + commons.php)

Archivos afectados (ambos proyectos LAESH y VOSK comparten la misma estructura):

  • www/laesh-swbldi/commons/DB.php — método handleQueryException()
  • www/restaurant/commons/DB.php — método handleQueryException()
  • www/laesh-swbldi/commons/commons.php — set_exception_handler()
  • www/restaurant/commons/commons.php — set_exception_handler()

Flujo completo cuando una query supera 10s:

  1. MariaDB ejecuta KILL del statement internamente (max_statement_time)
  2. MariaDB devuelve errno 1969, SQLSTATE HY000 al driver PDO
  3. PDO lanza PDOException con $e->errorInfo[1] === 1969
  4. DB::handleQueryException($e, $sql) detecta el código, escribe en log con nivel TIMEOUT e incluye la query SQL y backtrace
  5. set_exception_handler() en commons.php detecta $nativeCode === 1969:

15.9.2. Estrategia Elegida: OPcache PHP File Store

Fundamento de elección: El diagnóstico del servidor reveló OPcache ✓ instalado, pero APCu ✗, Redis ✗ y Memcached ✗. La estrategia A (OPcache PHP File Store) es la de mayor rendimiento alcanzable sin cambio de infraestructura:

  • El resultado de cada query se serializa como un archivo .php que retorna el array directamente: <?php return [...];
  • PHP lo carga vía include, que OPcache convierte en bytecode precompilado en RAM.
  • Los siguientes requests leen directamente desde RAM sin tocar disco ni red.
⚠️ PrivateTmp isolation (Hostinger KVM2): php8.3-fpm.service tiene PrivateTmp=true en Ubuntu 24.04. Los workers FPM ven un /tmp aislado (namespace de kernel propio). El caché debe estar en /opt/laesh/cache/ — nunca en /tmp/ — para que FPM y el cron www-data vean el mismo directorio físico. El env var LAESH_CACHE_DIR=/opt/laesh/cache se inyecta en php-fpm-laesh.conf y en /etc/cron.d/laesh-cache-renew. En local Docker no aplica (sin PrivateTmp).
⚠️ P-INFRA-02 — PHP CLI hang: OPcache JIT + Swoole (resuelto en 07_security_harden.sh): opcache.jit=tracing + opcache.enable_cli=1 + extension=swoole.so provoca hang indefinido en cualquier llamada php8.3 CLI. Afecta: cache_renew.cron (5 AM), 08_verify.sh, cualquier script CLI. Fix aplicado: paso 7 genera dos OPcache ini distintos: FPM → opcache.jit=tracing (rendimiento máximo en requests HTTP); CLI → opcache.jit=0 (bytecode caching sin JIT — sin hang). El cron y el verify script funcionan correctamente.

Patrón Cache-Aside (flujo completo):

Primera Request:
  PHP → MariaDB → fetch() → array PHP → serialize → /opt/laesh/cache/laesh_cache_prod_LAESH_CMS.php

15.9.10. Invalidación Granular en Publicaciones CMS y Purga Total vía URL (2026-09-03)

Para garantizar consistencia inmediata entre las publicaciones del CMS y el portal público index.php sin afectar el rendimiento global del servidor, se establecen dos mecanismos complementarios de gestión de memoria:

  • Invalidación Granular Automática (CMS POST /cms/save):

    Al confirmar una publicación en el CMS (admrc/index.php), el servidor no reinicia toda la memoria del sistema. Ejecuta Cache::invalidate($keys) especificando las claves canónicas afectadas según la sección modificada:

    • promociones → Cache::invalidate([Cache::KEY_PROMOS, Cache::KEY_CMS])
    • configuracion-general → Cache::invalidate([Cache::KEY_CFG, Cache::KEY_CMS])
    • especialidades → Cache::invalidate([Cache::KEY_TREE, Cache::KEY_CMS])
    • Cualquier otra sección CMS → Cache::invalidate(Cache::KEY_CMS)

    Técnicamente, Cache::invalidate($key) elimina el archivo serializado en /tmp/laesh_cache/ e invoca la función nativa de PHP opcache_invalidate($file, true), forzando la expulsión de la RAM únicamente para ese archivo de dataset, conservando los demás datasets intactos a velocidad <0.1 ms.

  • Purga Total e Inmediata vía URL (?reset_cache=1 / ?nocache=1):

    En situaciones de diagnóstico, migración o despliegue en caliente, el portal website/index.php detecta los parámetros GET de purga:

    • Invoca opcache_reset() para limpiar la totalidad del bytecode PHP en la RAM del proceso PHP-FPM worker.
    • Invoca Cache::clear() eliminando todos los archivos cacheados en /tmp/laesh_cache/.
    • Activa $_bypassCache = true forzando la re-consulta directa de todos los datasets desde MariaDB y regenerando la página completa.

16. Resiliencia del CMS — Gaps de Sesión, Red y Persistencia Local

Análisis de los escenarios de fallo identificados cuando un usuario CMS edita paneles del sitio web en tiempos desfasados (pausa de 2–4 horas entre ediciones), con red inestable o en sesiones largas. Se documenta el gap, el riesgo, la solución adoptada y la conclusión final.

16.1 Gap 1 — Volatilidad de Datos (El riesgo del Refresh)

Escenario: El usuario modifica 3 paneles durante la mañana. Pausa la edición por 3 horas. Al regresar, cierra la pestaña accidentalmente, el navegador suspende la pestaña por ahorro de RAM (comportamiento estándar de Chrome/Edge), o recarga la página.

Problema: Toda la información reside exclusivamente en el DOM (value de inputs y memoria interna de CKEditor 5). Al recargar o cerrar, el 100% del trabajo no publicado se pierde sin posibilidad de recuperación.

Solución — Draft Auto-Save (LocalStorage):

  1. Interceptar Cambios: Extender el módulo CmsDirtyTracker. Cada vez que detecte un cambio (markField), serializa el contenido del panel activo y lo guarda en localStorage (ej. clave: cms_draft_panel-hero).
  2. Recuperación al Cargar: Al cargar gestion_web.php, un script revisa si existen drafts en localStorage. Si existen, inyecta los valores en los campos, marca los puntos rojos (.cms-field-dirty-dot) y muestra una alerta: "Tienes cambios locales sin publicar en X pestañas. ¿Deseas restaurarlos o descartarlos?"
  3. Limpieza: Al ejecutar publishCmsSection() con éxito, se elimina la key correspondiente del localStorage.

16.2 Gap 2 — Expiración de Sesión y CSRF

Escenario: El usuario deja la ventana abierta 4+ horas. El token CSRF puede haber caducado, rotado, o el servidor puede haber reiniciado los workers de PHP-FPM, perdiendo el estado de sesión.

Problema: El usuario regresa y da clic en "Publicar". El fetch() hace el POST, pero el backend lo rechaza con 403 Forbidden (CSRF inválido) o 401 Unauthorized. El usuario se topa con un muro y no sabe cómo guardar sus datos antes de tener que recargar y perder todo.

Cobertura por Gap 1: Si el Draft Auto-Save está implementado, la consecuencia fatal (pérdida de datos) queda neutralizada. El usuario recarga, vuelve a autenticarse, y sus borradores se restauran automáticamente. El único costo restante es la fricción de UX (paso extra de login).

Solución Complementaria — session_lifetime dinámico en BD: La duración de sesión PHP ya no está hardcodeada en commons.php. Se lee desde la tabla configuraciones (clave: session_lifetime), editable en la UI de Administración del Sistema (pestaña "Proyecto 1: LAESH Sitio Web & CMS"). Valor actual: 518,400 seg = 6 días. Rango permitido en UI: 3,600 (1h) a 2,592,000 (30 días).

16.3 Gap 3 — Micro-Cortes de Internet

Escenario: El usuario termina de editar y presiona "Publicar". Justo en ese segundo, su WiFi tuvo un micro-corte o su Internet falló.

Problema: El fetch() arroja un TypeError: Failed to fetch. El toast rojo aparece, el DOM no se borra (lo cual es correcto), pero si el usuario recarga la página, pierde el trabajo.

Cobertura por Gap 1: Si el Draft Auto-Save está activo y el campo fue modificado antes de que el usuario presionara "Publicar", el borrador ya estaba guardado en localStorage. Al recargar tras el micro-corte, el contenido se restaura automáticamente.

Solución Complementaria — Sentinel de Red: Se puede añadir un listener a los eventos nativos window.addEventListener('offline') y online para deshabilitar preventivamente los botones "Publicar" y "Subir Imagen" cuando la red caiga, mostrando un banner flotante informativo.

16.4 Gap 4 — Imágenes Huérfanas (Activos sin Publicar)

Escenario: El usuario sube una imagen usando el slot de un carrusel. El script cms-upload.js la envía inmediatamente al backend y guarda el archivo en disco del servidor. El usuario nunca hace clic en "Publicar" (o cierra la pestaña).

Problema: La imagen fue subida físicamente al servidor pero la base de datos nunca se actualizó. Con el tiempo, el servidor se llenará de archivos "huérfanos" consumiendo espacio en disco.

Solución — Garbage Collector de Assets:

  1. Prefijo Temporal: cms-upload.php guarda la imagen en una carpeta /temp-uploads/ con un timestamp.
  2. Consolidación: Cuando el usuario ejecuta el POST final (publishCmsSection), el backend mueve la imagen a su carpeta definitiva /img/cms/ y actualiza la BD.
  3. Cron de Limpieza: Un script PHP (garbage_collector.php) ejecutado por el Programador de Tareas (Cron / systemd timer) elimina cualquier archivo en /temp-uploads/ con más de 24 horas de antigüedad.

Estado: Propuesta documentada. Pendiente de implementación.

17. Red de Seguridad CMS — Draft Auto-Save & beforeunload Guard (v2)

Este anexo documenta la implementación completa del sistema de protección de ediciones no publicadas en el CMS de LAESH, integrado en el módulo cms-dirty-tracker.js v2. La solución cubre tres vectores de riesgo de pérdida de datos simultáneamente sin introducir dependencias externas.

17.1 El Evento beforeunload — Análisis Técnico

El evento nativo del navegador beforeunload se dispara cuando el usuario intenta cerrar la pestaña, recargar la página (F5 / Ctrl+R), o navegar a otra URL desde la misma pestaña. Es el único mecanismo estándar del navegador para interceptar estos eventos antes de que ocurran.

NavegadorMuestra diálogoMuestra texto personalizadoAPI requerida
Chrome 119+✅ Sí (texto genérico del sistema)❌ No (ignora returnValue)e.preventDefault()
Firefox✅ Sí (texto genérico)❌ Noe.preventDefault() o e.returnValue = ''
Safari 16+✅ Sí✅ Parcialmente (muestra returnValue)e.returnValue = msg
Edge (Chromium)✅ Sí (texto genérico)❌ Noe.preventDefault()

Implementación adoptada: se usan las dos formas simultáneamente para máxima compatibilidad:

window.addEventListener('beforeunload', function(e) {
    if (!_hasDirtyFields) return;
    e.preventDefault();           // Estándar W3C — activa el diálogo en Chrome/Firefox/Edge
    e.returnValue = 'mensaje';    // Legacy — necesario para Safari; Chrome < 119 lo mostraba
    return 'mensaje';             // Fallback muy antiguo (IE, Chrome < 51)
});

Limitación conocida: El texto del mensaje NO es personalizable en Chrome, Firefox ni Edge modernos. El navegador muestra siempre su propio texto en el idioma del sistema (ej. "¿Abandonar el sitio? Es posible que los cambios que realizaste no se guarden."). Esto es una decisión de seguridad del navegador para evitar mensajes engañosos.

La bandera _hasDirtyFields: Variable de módulo (clausura del IIFE) que se mantiene sincronizada tras cada evalField(). Si _hasDirtyFields === false, el listener de beforeunload retorna inmediatamente sin activar el diálogo, evitando interrupciones cuando no hay cambios reales.

17.2 Draft Auto-Save — Arquitectura interna

El Auto-Save opera de forma completamente transparente y silenciosa para el usuario. No hay botones ni indicadores visuales propios — el usuario simplemente edita con normalidad y la red de seguridad trabaja en segundo plano.

Flujo de persistencia (cada vez que un campo cambia):

  1. evalField(el) detecta el cambio y llama a _saveDraft(panelEl).
  2. _saveDraft() itera todos los campos del panel y serializa solo los sucios (aquellos cuyo value difiere de dataset.original).
  3. Se guarda en localStorage con la clave cms_draft_{panelId} (ej: cms_draft_panel-hero).
  4. Formato JSON almacenado: { "timestamp": 1724600000000, "panelId": "panel-hero", "fields": { "nombre_campo": "valor_editado" } }
  5. Si el panel queda sin campos sucios (el usuario revirtió todos los cambios), el draft se elimina automáticamente para no acumular entradas obsoletas.

Criterios de expiración:

  • Borradores de más de 7 días se descartan automáticamente en el próximo arranque.
  • El borrador se elimina explícitamente al llamar a resetPanel() (tras publicación exitosa).

Resistencia a errores de localStorage:

  • Todas las operaciones de localStorage están envueltas en try/catch.
  • Si localStorage no está disponible (modo de incógnito extremo, quota excedida, browsers de prueba), el módulo falla silenciosamente y continúa operando sin Auto-Save, sin romper ninguna funcionalidad.

17.3 Draft Restore — Flujo de Recuperación al Cargar

Al iniciar el módulo (CmsDirtyTracker.init()), se ejecuta _restoreDraftsIfAny() antes de inicializar los baselines. Esto garantiza que la detección de borradores ocurre cuando los campos aún tienen sus valores originales de la BD.

  1. Se revisa localStorage para cada panelId en la lista de paneles activos.
  2. Se descarta cualquier borrador con más de 7 días de antigüedad.
  3. Si se encuentran borradores válidos, se inyecta en el DOM un banner amarillo fijo en la parte superior de la página con:
    • Los nombres legibles de los paneles con cambios pendientes.
    • Botón "✅ Restaurar": inyecta los valores del JSON en los campos del DOM y llama a evalField() por cada campo (activa dots rojos + badges).
    • Botón "🗑 Descartar": elimina los drafts de localStorage y cierra el banner.
  4. Si el usuario hace clic en "Restaurar", los campos quedan en el estado exacto en que los dejó en la sesión anterior, con todos los indicadores visuales activos.

Importante: Los estilos del banner son 100% inline (no dependen de gestion-web.css) para garantizar que sea visible incluso si el CSS falla en cargar.

20. Protocolo CMS → Seed → OCI

El CMS local (portal ADMRC → Gestión Web) es la fuente de verdad del contenido editorial (web_contenidos). El archivo 07_seed_catalogs.sql es el canal de sincronización hacia OCI. Este protocolo define el ciclo completo.

20.1. Principios de Diseño

  • SSOT: La BD local (laesh_db en Docker) es la fuente de verdad. OCI recibe una copia versionada.
  • REPLACE INTO: Desde 2026-08-25, 07_seed_catalogs.sql usa REPLACE INTO para web_contenidos. Garantiza que el seed siempre sobreescriba ediciones CMS en OCI, sin importar el estado previo.
  • No dump ad-hoc: No se dumpean tablas directamente a OCI. La exportación pasa por 04_export_cms_seed.sh que regenera el script SSOT.
  • DROP controlado: En OCI se siempre recrea la BD con setup_oci.sh --drop tras un cambio de contenidos. Evita acumulación de filas huérfanas.

21. Monitoreo de Servicios y Alertas SMTP (Hostinger KVM 2)

✅ Implementado: 2026-09-04. Desplegado por 07_security_harden.sh. Requiere LAESH_SMTP_PASS en entorno.

21.1. Arquitectura del Monitoreo

El script scripts/monitor_services.sh se instala como cron */10 * * * * root. Monitorea 4 servicios con lógica de reintento y anti-spam:

ServicioVerificaciónAlerta si
nginxsystemctl + curl http://127.0.0.1/3 reintentos fallidos (×30s)
mariadbsystemctl + SELECT 1 via .mariadb-root.cnf3 reintentos fallidos

https_e2ecurl -k https://127.0.0.1/laesh/ (stack completo)Solo si nginx OK; 3 reintentos

21.2. Lógica Anti-Spam y Cooldown

  • 3 reintentos separados por 30 s (RETRY_WAIT=30). Tiempo total antes de alertar: ~60 s. Distingue blip transitorio (red, restart breve) de caída real.
  • Si el servicio se recupera en cualquier reintento → no se envía alerta.
  • Cooldown 30 min por servicio — estado persistido en /opt/laesh/monitor/<svc>.last_alert. Evita spam si la caída persiste.
  • flock /tmp/laesh-monitor.lock — evita ejecuciones solapadas si un ciclo tarda más del intervalo de cron.

23. Logger.php — Filtro de Nivel Mínimo (commons/Logger.php)

✅ Implementado: 2026-09-04. El filtro evita que logs de menor severidad sean procesados (evita escrituras innecesarias en sys_logs y app.log en producción).

23.1. Orden de Severidad

DEBUG(0) → INFO(1) → WARN(2) → ERROR(3) → CRITICAL(4) → FATAL(5) → OFF(∞)

Un log de nivel N pasa solo si N ≥ nivel_mínimo_configurado. OFF silencia absolutamente todo.

23.2. Configuración Recomendada por Entorno

Entornoapp_log_levelResultado práctico
Producción (Hostinger)WARN (default)Solo WARN, ERROR, CRITICAL, FATAL → mínimo ruido en BD y archivo. Sin DEBUG/INFO.
Debug temporal en prodINFO o DEBUGActivar via tab Infra (§22.3); revertir a WARN cuando el problema esté resuelto.
Local Docker (APP_ENV≠production)N/A — automáticoSi APP_ENV no es production, el filtro usa DEBUG sin leer el archivo de conf.
Silencio total de emergenciaOFFNingún log pasa — usar solo si el volumen de I/O está causando problemas.

23.3. Implementación — Detalles Técnicos

  • El nivel se carga desde /opt/laesh/configs/app-log-level.php (archivo PHP que retorna array — OPcache lo compila a bytecode).
  • Se cachea en Logger::$minLevel (propiedad estática) el primer log() del request. Cero I/O en llamadas subsiguientes del mismo request.
  • Fallback: si el archivo no existe o tiene nivel inválido → usa WARN.
  • En entornos no-producción (APP_ENV !== 'production') → usa DEBUG directamente, sin leer el archivo.
  • Guard al inicio de log(): if (!self::passes($level)) return; — return temprano antes de cualquier conexión a BD.

24.3. Fix G-CERTBOT-01 — nginx TLS Duplicate (certbot --nginx vs domain.conf)

Gap ID: G-CERTBOT-01 · Severidad: Alta · Detectado: 2026-09-05

Causa Raíz

certbot --nginx modifica el site config de nginx en-place y añade include /etc/letsencrypt/options-ssl-nginx.conf. Ese include contiene ssl_protocols TLSv1.2 TLSv1.3 y ssl_ciphers …. Nuestro nginx-laesh-domain.conf ya tenía esas directivas → nginx reportaba "ssl_ciphers directive is duplicate" y fallaba el test.

Además, nginx-laesh-domain.conf usaba server_name _ y cert self-signed (era copia sin actualizar de nginx-laesh-ip.conf).

Fix Aplicado en Pipeline (fuente local)

  • 05_tls_certbot.sh — cambiado certbot --nginx a certbot certonly --webroot -w /opt/laesh/www. Certonly solo emite el cert, no toca el config de nginx. Sin conflicto de directivas TLS.
  • configs/nginx-laesh-domain.conf — reescrito como Modo B real:
    • server_name __LAESH_DOMAIN__ www.__LAESH_DOMAIN__; (placeholder → sed en script)
    • Cert paths: /etc/letsencrypt/live/__LAESH_DOMAIN__/fullchain.pem
    • HSTS activado: Strict-Transport-Security max-age=31536000; includeSubDomains
    • Sin default_server (Modo A/ip.conf lo retiene)
  • El script inyecta el dominio real con:
    sed "s/__LAESH_DOMAIN__/${LAESH_DOMAIN}/g" nginx-laesh-domain.conf > $NGINX_SITE

Fix Inmediato en Servidor (ejecutar manualmente)
