1. Nivel de Infraestructura y Servidor Web (Nginx & PHP-FPM)

Alineado a las políticas de arquitectura frugal y al Nginx Hardening. El servidor web es Nginx 1.27-alpine (Docker local) y Nginx 1.18.0 (OCI VM nativo). PHP se ejecuta vía PHP-FPM 8.3 como proceso separado.

1.1. Aislamiento y Ocultamiento de Identidad

  • Desactivar Firmas Nginx: Se debe configurar server_tokens off; en el bloque http de nginx.conf para evitar que escáneres identifiquen la versión del OS/Nginx. Entorno Docker Local Setup OCI VM
  • Restricción de Directorios: Nginx no tiene indexación por defecto (autoindex off). Bloquear accesos a archivos sensibles con location ~ /\.(env|git|sql|ini) { deny all; }. Entorno Docker Local Setup OCI VM
  • Restricción de Métodos HTTP: Limitar los verbos permitidos a GET, POST y HEAD con if ($request_method !~ ^(GET|POST|HEAD)$) { return 405; }. Setup OCI VM

1.2. Headers de Seguridad HTTP Setup Hostinger KVM

  • X-Frame-Options "SAMEORIGIN" (Mitiga Clickjacking en ambos portales).
  • X-XSS-Protection "1; mode=block" (Defensa activa contra Cross-Site Scripting).
  • X-Content-Type-Options "nosniff" (Previene escalamiento de privilegios por MIME-sniffing).
  • Strict-Transport-Security (HSTS) para obligar a los navegadores a interactuar exclusivamente sobre canales seguros.

1.3. Entorno PHP-FPM 8.3

  • Seguridad Base en php.ini: Uso de expose_php = Off, display_errors = Off, y log_errors = On para prevenir fugas de información. Entorno Docker Local Setup Hostinger KVM
  • Bloqueo de Funciones Peligrosas: Habilitar disable_functions = exec, passthru, shell_exec, system, popen para impedir la ejecución de comandos de terminal si el código fuese comprometido. Setup Hostinger KVM
  • Prevención de DoS (Límites de Carga): Restringir upload_max_filesize y post_max_size a un máximo de 5MB. Estos límites base se gestionarán dinámicamente desde la tabla global configuraciones en la base de datos, blindando el servidor contra ataques de denegación de servicio por saturación de disco o ancho de banda. Setup Hostinger KVM Desarrollo
  • Aislamiento de Uploads (Archivos PDF): El directorio de almacenamiento de PDFs de resultados estará protegido con un location block en Nginx que prohiba explícitamente la ejecución de cualquier script (ej. location ~* /uploads/.*\.php$ { deny all; }). No se usan .htaccess — Nginx no los procesa. Despliegue

1.4. Cifrado en Tránsito (HTTPS) Setup Hostinger KVM

  • Emisión y renovación automática (cron) de certificados SSL/TLS vía Certbot (Let's Encrypt).
  • Desactivación de protocolos obsoletos (SSLv3, TLS 1.0, TLS 1.1) y cifrados débiles (aNULL, MD5, 3DES). Soporte estricto para TLSv1.2 y TLSv1.3.

1.5. Acceso al Servidor y Sistema Operativo (SSH) Setup Hostinger KVM

  • Hardening SSH: Deshabilitar por completo el inicio de sesión del usuario root (PermitRootLogin no).
  • Autenticación Criptográfica: Forzar el uso exclusivo de llaves SSH (ED25519/RSA), inhabilitando los inicios de sesión por contraseña plana (PasswordAuthentication no).

2. Nivel Base de Datos (MariaDB)

  • Blindaje de Red Perimetral: El servidor MariaDB escuchará peticiones únicamente en la interfaz de loopback 127.0.0.1. Se debe aplicar bloqueo perimetral explícito del puerto 3306 mediante el firewall UFW. Setup Hostinger KVM
  • Principio de Mínimos Privilegios (Least Privilege) — Automatizado: Las credenciales utilizadas por Flight PHP (laesh_app) tienen únicamente permisos DML: SELECT, INSERT, UPDATE, DELETE ON laesh_db.*. Los permisos destructivos (DROP, ALTER, ALL PRIVILEGES) quedan revocados. Implementación: setup_hostinger.sh paso 3b ejecuta automáticamente REVOKE ALL PRIVILEGES + GRANT SELECT,INSERT,UPDATE,DELETE después de que el schema completo (10 scripts SQL DDL) está instalado — garantiza que la cuenta de app nunca tenga acceso DDL en runtime de producción. 08_verify.sh verifica que no haya GRANT ALL activo. Setup Hostinger KVM Despliegue

3. Nivel de Aplicación (Micro-Framework Flight PHP)

3.1. Prevención de Inyecciones Desarrollo

  • Inyección SQL (SQLi): Implementación obligatoria del envoltorio \Common\DB::connect() con Sentencias Preparadas (Prepared Statements) a través de PDO. Queda estrictamente vetada la concatenación de variables puras en strings SQL.
  • Cross-Site Scripting (XSS): Todo output de texto dinámico en el Frontend será sanitizado y escapado empleando la función nativa del motor de plantillas League\Plates ($this->e($variable)), la cual abstrae de forma segura el uso de htmlspecialchars.

3.2. Protección de Formularios y APIs Desarrollo

  • Cross-Site Request Forgery (CSRF): Implementación de Tokens de Idempotencia o Tokens anti-CSRF transaccionales en operaciones críticas (ej. creación de órdenes o guardado de resultados).
  • Mitigación de Lógica (HTMX): Las validaciones del servidor para endpoints llamados por HTMX devolverán el header especial HX-Redirect: /login ante fallos de autorización (401/403) para forzar redirecciones limpias y no anidar pantallas de login en los contenedores DOM.
  • Fuerza Bruta (Rate Limiting): El login administrativo y operativo será vigilado por la tabla users_throttling de Delight Auth, bloqueando de manera automática las direcciones IP tras múltiples intentos de inicio de sesión fallidos.

4. Nivel Autenticación y Ciclo de Sesión (Delight Auth)

4.1. Criptografía y Reglas de Identidad Desarrollo

  • Hash Bcrypt Nativo: Siguiendo el estándar, toda contraseña (incluyendo la inicial derivada de la fecha de nacimiento ddmmaaaa) será empaquetada y cifrada con Bcrypt y Salting automático directamente por Delight Auth. No existirá almacenamiento plano.
  • Identidad Única (Login): El nombre de usuario oficial del personal operativo siempre corresponderá a su Número de Teléfono Móvil (10 dígitos).

4.2. Persistencia y Control Anti-Suplantación (Session Hijacking)

  • Cookies Seguras: Toda cookie de sesión tendrá adheridas las banderas HttpOnly (blindando accesos vía JS) y Secure (exigiendo canal HTTPS). Entorno Docker Local Despliegue
  • Fijación de Sesión (Session Fixation): Tras un login exitoso, el sistema disparará un session_regenerate_id() para invalidar el token anterior y prevenir el robo de sesión preestablecido. Desarrollo
  • Modelo Multiusuario Atómico: Al compartir un equipo físico (Recepción), la introducción de nuevas credenciales debe buscar y destruir activamente cualquier token persistente de Remember Me del usuario anterior en users_remembered, aislando los datos por completo. Desarrollo
  • Ciclo Dual (24h / 28d): Configuración de sesión de servidor limitada a 24 horas (`gc_maxlifetime`). Se activará el uso de la cookie Remember Me a 28 días para resistir el cierre imprevisto por suspensión de red (Doze) en dispositivos móviles. Desarrollo Setup Hostinger KVM

4.3. Arquitectura de Blindaje en 3 Niveles (index.php y Modal de Acceso) Desarrollo

Para prevenir colisiones de sesión en navegadores multi-pestaña y evitar la suplantación de identidad entre roles (Médico, Recepción, Administrador), se implementó un modelo de protección tripartito:

  • Nivel 1 — Navegación de Sesión Unirepresentativa (Frontend): El envío del formulario modal de login efectúa la navegación en la misma pestaña (window.location.href = portalUrl). Esto impide que queden pestañas "huérfanas" abiertas con la sesión de un rol anterior mientras se interactúa con una sesión nueva.
  • Nivel 2 — Guardias de Verificación RBAC en Servidor (Backend): Tanto los routers de entrada (/laesh/adrc/, /laesh/rc/, /laesh/md/) como las APIs operativas (POST /cms/save) ejecutan una consulta estricta a Flight::rbac()->requirePermission('permiso'). Peticiones no autorizadas son interceptadas con HTTP 302/403 antes de renderizar vistas o procesar DML.
  • Nivel 3 — Destrucción Atómica de Sesión y CSRF Rotativo: Al procesar un POST de inicio de sesión, el servidor invoca explícitamente Flight::auth()->logOut() antes de autenticar al nuevo usuario, purgando cookies y tokens pasados para garantizar un aislamiento del 100%. Adicionalmente, el token CSRF transaccional es validado y rotado mediante hash_equals().

4.4. Buenas Prácticas de Manipulación DOM y Cumplimiento CSP Desarrollo

  • Prohibición Estricta de Parches Inline: Queda strictly vetado el uso de atributos de eventos incrustados en HTML (ej. onclick="...", onchange="..."). Las políticas defensivas del servidor mediante Content-Security-Policy: script-src 'self' bloquean la ejecución de código embebido por seguridad contra vectores XSS.
  • Delegación Global de Eventos (JS Centralizado): La interacción de apertura de logotipos corporativos y navegación a nueva pestaña (target="_blank") se resolvió mediante delegación de eventos centralizada en la fase de captura (useCapture: true) dentro de app.js: 
    document.addEventListener('click', function(e) {
    var a = e.target.closest('a.logo, a.portal-access-link');
    if (a && a.getAttribute('target') === '_blank') {
        e.stopPropagation();
    }
}, true);
    Esta arquitectura garantiza que el navegador procese la acción sin interferencias de scripts locales de la interfaz privada y respetando el estándar User Activation.

4.5. Segmentación Granular RBAC en Interfaces de Usuario (Portales /laesh/rc/, /laesh/md/ y /laesh/adrc/) Desarrollo

Para garantizar que el principio de mínimos privilegios se extienda al renderizado DOM en las vistas Plates PHP de los portales privados, se aplican reglas de ocultamiento dinámico server-side:

  • Aislamiento de la CMS Admin (/laesh/adrc/): Acceso exclusivo para el perfil ADMIN mediante la guardia RBAC Flight::rbac()->requirePermission('gestionar_cms'). El enlace de navegación Contenidos del Sitio Web (#nav-gestion-web) en la barra lateral de Recepción está envuelto en <?php if (!empty($isAdmin)): ?> y no se expone a los usuarios de rol RECEPCION.
  • Ocultamiento de Módulo Médicos y Operaciones en Recepción (/laesh/rc/): El ítem de menú Médicos (nav-item), el panel de control #panel-medicos y la columna Operaciones de gestión de credenciales se encuentran condicionados por <?php if (!empty($isAdmin)): ?>. Para el personal de Recepción estándar, estos nodos quedan 100% excluidos del renderizado HTML por el servidor.
  • Aislamiento del Portal Médico (/laesh/md/): Acceso restringido al perfil MEDICO o usuarios con permiso ver_ordenes_propias, asegurando que los profesionales médicos interactúen únicamente con su catálogo de solicitudes digitales sin visibilidad sobre las operaciones globales del laboratorio.

5. Defensas Contra Vectores No Típicos (Logic Flaws) Desarrollo

  • Inyección de Archivos Nocivos (PDF Uploads): Al adjuntar resultados, el sistema backend validará no solo la extensión, sino la firma binaria real (Magic Number %PDF-) mediante la extensión finfo. Si el archivo es un script malicioso enmascarado, será rechazado y eliminado instantáneamente.
  • Inseguridad de Referencias Directas (IDOR) y Suplantación Médica: Todas las descargas de PDFs e historiales médicos ejecutarán una validación cruzada. El controlador en Flight PHP verificará que el orden_id solicitado coincida exactamente con el medico_id de la sesión de Delight Auth. Intentos de acceso a folios de otros profesionales dispararán un 403 Forbidden y un log de alerta a sys_logs.
  • Autorización de Recursos (RBAC): Cada ruta ejecutará una validación obligatoria contra \Common\RbacManager asegurando que Recepción, Médicos y Administración interactúen estrictamente en su perímetro funcional.
  • Protección del Panel de Sistema y Logs (/laesh/adrc/sistema): La administración de configuraciones y la visualización de logs de aplicación (sys_logs, fallback_log, app.log, Nginx y PHP-FPM) están restringidas por la guardia RBAC gestionar_cms para el rol ADMIN. Se previene Path Traversal restringiendo la lectura de archivos planos a la lista blanca de rutas conocidas.
  • Validación Rigurosa de Binarios en CMS Upload: La subida de imágenes analiza el tipo MIME real mediante \finfo (MIME Types permitidos: WebP, JPEG, PNG). Se aplica sanitización al nombre del slot (alfanumérico y guiones únicamente) y rotación dinámica del token CSRF tras cada subida.
  • Protección de Bypass de Caché L2 (DoS Prevention): La estrategia de Caché OPcache File Store soporta un parámetro de derivación (?_preview=1) para la previsualización del CMS. Este vector está severamente protegido en index.php: se requiere una sesión activa con rol de ADMIN, que existan datos en el borrador temporal de la sesión (cms_draft), y validación estricta de variables. Si no se cumplen estas precondiciones, el motor ignora el parámetro y sirve el contenido desde la RAM, bloqueando ataques de agotamiento de caché (Denegación de Servicio).

6. Monitoreo de Servicios y Alertas SMTP Setup Hostinger KVM

El pipeline KVM2 incluye infraestructura de monitoreo activo con alertas via correo electrónico. Su relevancia de seguridad es directa: detecta caídas de servicios críticos antes de que se conviertan en incidentes, y protege las credenciales SMTP con controles estrictos.

6.1. Seguridad de Credenciales SMTP (swaks)

  • Nunca hardcodeadas en el repositorio: La contraseña de la cuenta de alertas usa el placeholder __SMTP_PASS__ en el archivo fuente (configs/swaks.conf). El valor real se inyecta en tiempo de deploy desde la variable de entorno LAESH_SMTP_PASS por 07_security_harden.sh, que usa sed con sustitución en memoria — la contraseña nunca toca el disco en texto claro en el repo.
  • Archivo con permisos mínimos: /opt/laesh/configs/swaks.conf se despliega con chmod 600 root:root. Solo root puede leerlo; el proceso de alerta (monitor_services.sh) corre como root via cron, por lo que es el único que necesita acceso.
  • Protocolo seguro: Yahoo SMTP en puerto 587 con STARTTLS + autenticación LOGIN. No se usa SMTP sin cifrar (puerto 25) ni autenticación en claro.
  • Smoke test post-deploy: scripts/test_smtp.sh verifica en 4 pasos que no quede el placeholder sin sustituir antes de declarar el deploy exitoso. Retorna exit code clasificado (1=preflight, 2=conexión/auth, 3=envío) para diagnóstico preciso.

6.2. Diseño Anti-Abuso del Monitor

  • Cooldown anti-spam (30 min): El estado por servicio se persiste en /opt/laesh/monitor/<svc>.last_alert. Una caída sostenida solo genera una alerta cada 30 minutos — previene inundación de bandeja si el servicio no se recupera.
  • flock (mutex de proceso): El cron usa flock -n /tmp/laesh-monitor.lock. Si un ciclo previo está en sus reintentos (retención del lock hasta ~61 s en peor caso), el siguiente disparo de cron sale inmediatamente sin crear un proceso paralelo.
  • Reintentos antes de alertar: 3 verificaciones × 30 s — distingue reinicios transitorios (swap de kernel, OOM killer puntual, restart de servicio) de caídas reales. Evita falsas alarmas por eventos de mantenimiento normales.
  • Verificación https_e2e subordinada a nginx: El check de stack completo (curl https://127.0.0.1/laesh/) solo se ejecuta si nginx ya está OK. Previene alertas duplicadas cuando Nginx caído ya generó su propia alerta.

6.3. Trazabilidad del Monitor

  • Log estructurado: /opt/laesh/logs/monitor-services.log registra cada ciclo con timestamp ISO-8601: [START], cada [FAIL N/3], [RECOVERED] si se recuperó en reintento, [ALERT] cuando se envía email, [COOLDOWN] con segundos restantes, y [END].
  • Estado auditado: Los archivos .last_alert tienen timestamp Unix — es posible consultar cuándo fue la última alerta de cada servicio sin leer el log completo.
