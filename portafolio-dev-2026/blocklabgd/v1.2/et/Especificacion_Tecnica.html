1. Resumen Ejecutivo Técnico

  • Proyecto 1: Sitio Web Corporativo (Público): Plataforma pública con panel de administración para editar banner, servicios y promociones. Optimizado para SEO y Google Ads para captación de pacientes.
  • Proyecto 2: Bloc Digital vía Internet (Privado): Ecosistema web privado para la automatización y rastreo de solicitudes de estudio de laboratorio. Conecta a médicos tratantes (orden digital) y recepción (gestión de atención y carga de resultados PDF) con notificaciones instantáneas bidireccionales en tiempo real.

Pilares Tecnológicos del Sistema

  • Autenticación y Seguridad: Delight PHP Auth, control de sesiones RBAC y protección anti-resubmit.
  • Backend: Flight PHP (micro-framework), PDO/MariaDB 11, Swoole v6 para WebSockets en tiempo real.
  • Frontend — Arquitectura CSS: Cascade Layers (@layer base, website, portal-utils); split físico entre landing y portales; fuentes locales WOFF2 offline-safe.
  • Frontend — Arquitectura JS: Vanilla JS + HTMX; un módulo JS por página (no bundle monolítico); device-detect.js + medicos-a11y.js para A11Y/WCAG 2.1.
  • Frugalidad del Stack: Sin frameworks CSS/JS externos (no Bootstrap, no Vue). CMS nativo en BD. Autoloader PSR-4 compartido. Cache-busting automático vía bump-versions.sh.
  • Notificaciones Híbridas: Persistencia SSOT en tabla notificaciones (slow-path) + WebSocket Swoole (fast-path) + auto-reconexión con backoff exponencial.

El flujo detallado es:

  1. Captura y Envío: El Médico completa el formulario de solicitud en su portal móvil/desktop. Al enviar, HTMX intercepta el evento y lanza una petición POST asíncrona (AJAX).
  2. Validación y Persistencia (QoS - Slow-Path): El servidor PHP-FPM recibe la solicitud, verifica el token de sesión y los permisos RBAC. Si es exitoso, graba de forma transaccional la orden y, **obligatoriamente antes de lanzar la notificación en tiempo real**, inserta una alerta marcada como no leída en la tabla notificaciones de MariaDB. Esto garantiza la integridad y entrega de la alerta en caso de desconexión del cliente.
  3. Inter-Process Communication (Bridge HTTP): El controlador de PHP-FPM envía una petición HTTP POST asíncrona no-bloqueante a la URL del contenedor de Swoole (http://swoole:9502/publish) compartiendo el folio y los metadatos de la notificación.
  4. Respuesta al Emisor: El backend PHP-FPM responde inmediatamente al Médico con un fragmento HTML de éxito (HTTP 200), cerrando su hilo de ejecución.
  5. Notificación Activa (QoS - Fast-Path): El servidor Swoole v6 recibe el POST HTTP por la red de Docker y realiza un broadcast por WebSocket (a través de Nginx) a los clientes Recepción suscritos. El navegador intercepta este payload, reproduce el silbato de alerta y renderiza la burbuja UI.

2.2.1. Ciclo de Vida General de una Petición HTTP / HTMX

  1. Disparo e Interceptación (Cliente): El usuario realiza una acción (ej. clic o envío). El motor de HTMX (Vanilla JS) intercepta el evento nativo del navegador, cancela la recarga completa de la página y empaqueta los datos de los formularios de forma asíncrona.
  2. Enrutamiento y Seguridad (Servidor - Nginx/Flight): La petición HTTP llega a Nginx, que la delega a PHP-FPM y es despachada por Flight PHP. Lo primero que ejecuta el controlador es la verificación de sesión y permisos a través del objeto PDO centralizado de Delight-PHP/Auth y las reglas del RBAC Personalizado. Si el usuario no tiene permisos, se detiene el flujo y se retorna un fragmento HTML de error.

⚠️ Regla de Oro para Redirecciones en Flight PHP:
Debido a que el sistema opera bajo una subcarpeta (ej. /laesh/ en la configuración LAN / localhost), el enrutador de Flight PHP autodetecta este contexto y lo añade dinámicamente como prefijo a todas las llamadas del método Flight::redirect().

  • Incorrecto: Flight::redirect('/laesh/login'); (Produce un desvío inválido a /laesh/laesh/login que desencadena errores 404).
  • Correcto: Flight::redirect('/login'); (Flight resolverá dinámicamente la URL física como /laesh/login en runtime).
La única excepción aplicable son las respuestas para peticiones HTMX manejadas desde el cliente mediante HTMX u otros métodos de red directos, donde se debe inyectar manualmente la ruta absoluta usando la cabecera HTTP nativa header("HX-Redirect: /laesh/");.

2.4b. Mecanismo de Notificación Híbrido (Bridge PHP-Swoole & QoS)

Para asegurar una entrega garantizada de notificaciones críticas a los médicos y al personal de recepción sin la sobrecarga de un broker externo (como MQTT), se implementa una arquitectura híbrida desacoplada:

2.4.1. El Puente de Comunicación (PHP-FPM ➔ Swoole IPC)

Dado que Flight PHP corre bajo el ciclo de vida limitado de PHP-FPM en Nginx, no puede mantener sockets abiertos. La interoperación entre entornos se resuelve mediante un Bridge HTTP asíncrono unidireccional:

// Flujo en Controlador (PHP-FPM) — schema completo con QoS
// 1. Persiste el evento en la BD ANTES de emitir (garantía slow-path)
$notif_id = $db->query("
  INSERT INTO notificaciones
    (user_id, tipo, folio_referencia, mensaje, url_enlace, entregado_ws, retry_count, leido)
  VALUES
    (:uid, :tipo, :folio, :msg, :url, 0, 0, 0)
", [...]);  // entregado_ws=0, retry_count=0 → pendiente

// 2. Dispara el HTTP POST interno a Swoole de forma no-bloqueante
$ok = \Common\Notifier::emit($notif_id, [
    'tipo'             => 'nueva_orden',   // 'nueva_orden' | 'resultados_listos'
    'folio_referencia' => $folio,          // ej: LAESH-00001 (enlace rápido sin JOIN)
    'user_id'          => $medico_id,
]);

// 3. Si Swoole confirma broadcast, marcar entregado_ws=1
if ($ok) {
    $db->query("UPDATE notificaciones SET entregado_ws=1 WHERE id=:id", ['id'=>$notif_id]);
}
// Si falla (timeout 2s): entregado_ws permanece 0 → fallback poll AJAX lo retomará

La clase \Common\Notifier realiza una llamada HTTP POST a http://swoole:9502/publish (dirección interna del contenedor Swoole en la red Docker) con un CURLOPT_TIMEOUT ultra-corto (máximo 2 segundos) para evitar congelar el hilo HTTP del cliente si el servidor de notificaciones estuviera inactivo.

2.4.2. Estrategia de QoS (Calidad de Servicio) de Aplicación

El protocolo WebSocket carece de un mecanismo nativo de QoS. Para resolver las pérdidas de paquetes por bloqueos de pantalla, cortes de red móvil o reinicios del servidor Swoole, se implementa una estrategia de tres capas con trazabilidad completa en la tabla notificaciones:

  • Slow-Path — Garantía de Persistencia (SSOT): La tabla notificaciones de MariaDB es la Fuente Única de Verdad. Toda alerta se escribe atómicamente con entregado_ws=0, retry_count=0, leido=0 antes de intentar el broadcast en tiempo real. El campo tipo (ENUM: nueva_orden | resultados_listos) y folio_referencia permiten construir el enlace directo a la orden sin JOIN adicional en la UI.
  • Fast-Path — Entrega Inmediata: Swoole v6 recibe el POST en su puerto HTTP local e inmediatamente hace broadcast por WebSocket a todos los clientes suscritos del rol correspondiente. Si el broadcast tiene éxito, el controlador marca entregado_ws=1 en la fila. El navegador intercepta el payload, reproduce el silbato de alerta (recepción) o muestra badge silencioso (médico) y renderiza la burbuja UI.
  • Sincronización Fallback — Poll AJAX con Backoff: El cliente JS implementa auto-reconexión con backoff exponencial (1s → 2s → 4s → 8s, máx 30s). Al reconectar exitosamente, dispara GET /notificaciones/pendientes que filtra WHERE (entregado_ws=0 OR leido=0) AND user_id=:uid. El servidor incrementa retry_count en cada recuperación por poll. Una vez que el cliente confirma la recepción (click en badge o cierre de panel), se envía PATCH /notificaciones/:id/leido y el servidor setea leido=1. Esto garantiza entrega eventual incluso en contextos de conectividad degradada (clínicas con WiFi inestable).

Los campos entregado_ws y retry_count también sirven como métricas operativas: un alto retry_count promedio es indicador de inestabilidad de la conexión WS y puede disparar alertas de observabilidad en sys_logs.

2.4.3. Rutas de Escalabilidad Futura (Eficiencia y Rendimiento)

La arquitectura descentralizada actual garantiza eficiencia frugal para un volumen de laboratorio (overhead IPC de ~1-2ms vía cURL). En caso de escalar a grandes volúmenes transaccionales, se han identificado las siguientes vías de optimización:

  • Server-Side (Bridge IPC): Sustituir el puente HTTP actual por un broker en memoria (Pub/Sub en Redis) o por Sockets UNIX locales (unix://) para eliminar el overhead de la capa TCP/HTTP entre PHP-FPM y Swoole.
  • Server-Side (Consultas DB en Swoole): Si Swoole requiere interactuar directamente con MariaDB, se deberá usar exclusivamente el conector Swoole\Database\PDOPool. Este Connection Pool en corrutinas pausa la ejecución mientras espera a la DB, garantizando un I/O asíncrono puro sin bloquear al worker.
  • Client-Side (Payloads WSS): Actualmente se despacha JSON plano. Si la latencia en redes Edge/3G se volviera un cuello de botella, el payload se puede optimizar al máximo empaquetándolo en formato binario MessagePack en el servidor antes del broadcast, omitiendo la activación de compresión (permessage-deflate) la cual desperdiciaría CPU en payloads tan cortos.

3.3. Filosofía de Frugalidad del Stack

Para cumplir con los principios de desarrollo ligero y optimización de recursos locales, el ecosistema LAESH implementa dos patrones de frugalidad a nivel de software:

3.3.1. Cargador de Dependencias Compartido (Frugal Autoloader)

En lugar de instalar y duplicar de forma física las librerías vendor (Flight PHP, Delight Auth, League Plates) en el directorio de cada aplicación web, se diseñó un **Autoloader PSR-4 compartido** en laesh-swbldi/commons/autoload.php. Este cargador mapea las llamadas de dependencias externas directamente al subdirectorio paralelo restaurantb/commons/libs/:

// Mapeos del Autoloader en LAESH
$sharedLibsDir = __DIR__ . '/../../restaurantb/commons/libs';
// ...
'League\\Plates\\'  => $sharedLibsDir . '/plates/',
'Delight\\Auth\\'   => $sharedLibsDir . '/auth/Delight/Auth/',
'Common\\'          => __DIR__ . '/', // Local a LAESH

Esto reduce la huella de almacenamiento en disco en más del 80% y evita el traslape o divergencia de dependencias de infraestructura entre los proyectos hermanos, manteniendo un único núcleo de bibliotecas estables compartidas.

3.3.2. Bootstrap Global Unificado (commons.php)

La inicialización del entorno se centraliza en laesh-swbldi/commons/commons.php, el cual realiza las siguientes operaciones transversales en cada llamada HTTP:

  • Parámetros de Sesión Seguros: Fuerza las directivas session.cookie_httponly = 1, session.use_only_cookies = 1 y un ciclo de vida extendido de cookies y recolector de basura de 24 horas (86,400s) para soportar sesiones persistentes en los portales clínicos.
  • Capturador Global de Fallos: Intercepta errores y excepciones de PHP mediante gestores nativos redireccionados a \Common\Logger, evitando mostrar trazas del sistema (stack traces) en producción y garantizando que se guarde un registro físico.
  • Inyección de Dependencias: Registra e inicializa Delight\Auth\Auth, el gestor de accesos RbacManager, Plates (views engine) y la conexión PDO singleton en el router Flight PHP.

3.3.3. Estrategia de Pool de Conexiones a Base de Datos (PHP-FPM)

Dada la arquitectura share-nothing de PHP bajo Nginx/PHP-FPM, no existe un hilo centralizado de memoria para administrar pools tradicionales. Para evitar el costo de reconexión TCP (~5-30ms por petición HTMX) se aplica el atributo PDO::ATTR_PERSISTENT => true en la clase Common\DB:

  • Pool a nivel de Proceso FPM: Cada worker activo mantiene en caché la conexión a MariaDB. Al atender peticiones consecutivas, reutiliza la conexión abierta de forma transparente.
  • Aislamiento en Swoole v6: Si en futuras fases el servidor de WebSockets requiere consultar MariaDB directamente, se utilizará obligatoriamente la clase nativa Swoole\Database\PDOPool para arrendar conexiones por corrutina de manera segura sin colisionar el socket.

3.4. Configuración de HTMX en el Ecosistema Ligero

La adopción de HTMX permite construir una SPA (Single Page Application) ligera manteniendo el control del estado y del HTML en el servidor (Flight/Plates). Las directivas de integración clave son:

  • hx-boost: Habilitado globalmente para interceptar todas las etiquetas y formularios de la aplicación, convirtiendo las recargas tradicionales en llamadas HTMX transparentes.
  • Intercambios Fuera de Banda (OOB): Utilizado activamente (hx-swap-oob="true") para actualizar elementos de interfaz remotos (ej. barra de estado del recepción, breadcrumbs, totales del día) en una única respuesta HTTP, sin necesidad de realizar múltiples peticiones HTMX paralelas.
  • Control de Retroalimentación de UI: Se configuran las clases .htmx-request y hx-indicator para activar automáticamente spinners e indicadores de carga globales, previniendo la frustración del usuario en llamadas lentas.

5.1. Generación Dinámica de Solicitudes Digitales en PDF (On-The-Fly)

  • Ventajas del Modelo: Garantiza que cualquier cambio posterior en los datos del paciente o en el catálogo de estudios se refleje inmediatamente en el documento descargado, evitando la acumulación de archivos obsoletos.

5.3.3. Gestión de Imágenes y Activos Multimedia

El sitio público tiene dependencia de aproximadamente 40 imágenes estáticas almacenadas en /laesh-web-assets-uipv1a/img/. El CMS debe soportar la actualización de estas imágenes bajo las siguientes modalidades, ordenadas por preferencia de implementación:

  1. Modalidad A — Rutas por BD (mínimo viable): El administrador sube los archivos al servidor vía SFTP/SCP y registra únicamente la ruta en web_contenidos (campo imagen_url). El CMS no gestiona el archivo físico, solo la referencia.

La ruta resultante se persiste en web_contenidos.

En ambas modalidades, la inyección del Hero (sección slider) en index.php requiere un manejo dinámico desde PHP, evaluando el estado del switch "Pausar el slider y fijar esta imagen de fondo" configurado en el CMS:

  1. Slider de Imágenes Activo (Transiciones Habilitadas)
    • En el CSS (ej. landing.css o estilos en línea generados dinámicamente), se deben construir las 4 clases de fondo (.bg-slide-1 a .bg-slide-4) asignándoles sus respectivas imágenes (ej. recepcion-de-pacientes.webp, recepcion.webp, etc.).
    • En el <head> de index.html, el sistema PHP debe imprimir la etiqueta <link rel="preload" as="image" fetchpriority="high"> apuntando de manera dinámica a la imagen que corresponde al Slide 1, optimizando así la métrica LCP (Largest Contentful Paint).
  2. Slider Inactivo (Una Sola Imagen Fija)
    • El backend debe inyectar la imagen única cargada por el usuario (ej. laesh-slider-futurista-c.webp) para que sobrescriba el fondo del Hero.
    • El <link rel="preload"> del LCP debe apuntar dinámicamente a esta única imagen personalizada.
⚠️ Atención Crítica en el Autorefresh del Caché (Cache Busting):
Cuando el usuario aplique cambios en el slider desde el CMS, el código PHP está obligado a incorporar un mecanismo de invalidación de caché (ej. anexar ?v=timestamp_de_actualizacion) en la etiqueta de carga de landing.css y en las rutas de las imágenes. De omitirse esta regla, los navegadores (especialmente móviles como Safari o Chrome en iOS/Android) retendrán la versión en caché del CSS/imágenes agresivamente y los cambios no se visualizarán en producción tras guardar.

5.3.4. Políticas de Carga de Assets y Aspectos Críticos del CMS

Estrategia Recomendada: Automatización en Backend (Poka-Yoke)

Para garantizar que el rendimiento del sitio web no se degrade con el tiempo debido a la carga de imágenes no optimizadas por parte del personal del laboratorio (médicos o recepcionistas), el CMS incorporará un motor de procesamiento de imágenes automatizado (Poka-Yoke):

  • Al recibir una imagen en el endpoint de carga, el backend en PHP (usando la extensión GD o Imagick) debe convertirla automáticamente a formato WebP (calidad 80%).
  • El motor de procesamiento debe redimensionar las dimensiones de la imagen al vuelo: un ancho máximo de 1920px para imágenes tipo Hero/Slider, y un ancho máximo de 1000px para el resto de las secciones.
Restricciones Estrictas de Carga (En caso de carga directa sin auto-procesamiento)
⚠️ Especificación desactualizada. La implementación en producción difiere de los valores de diseño aquí indicados:
  • Formato actual implementado: image/webp únicamente — no se admiten PNG ni JPEG directamente. El operador pre-procesa las imágenes con Squoosh antes de subir.
  • Pesos por sección (actuales): Hero ≤ 120 KB · Carrusel/Calidad ≤ 25 KB c/u · lunes.webp ≤ 70 KB · Croquis ≤ 90 KB.

  • Formatos Permitidos: Únicamente se aceptarán archivos con extensión .png y .jpeg / .jpg (tipos MIME: image/png, image/jpeg). Queda estrictamente prohibida la carga de formatos BMP, GIF o TIFF.

  • Limpieza de Formato en Textos: Para evitar que el personal copie textos enriquecidos desde Microsoft Word y rompa el diseño tipográfico institucional (fuentes Gill Sans MT y Cabin), el editor WYSIWYG del CMS debe configurarse con paste_as_text: true para forzar el pegado de texto plano.

  • Vigencia Automatizada de Promociones: Para evitar que banners de ofertas obsoletas sigan visibles, las promociones del CMS contarán con campos de rango de fechas (fecha_inicio y fecha_fin). El motor de renderizado filtrará automáticamente las promociones en base a la fecha del servidor.

No se usan CDNs externos de tipografías (Google Fonts, Bunny Fonts) — se elimina toda dependencia de red para renderizar texto. Las etiquetas <link rel="preconnect"> a servidores de Google Fonts quedan obsoletas y no deben incluirse.
  • Evitar Cascada de @import en Hojas de Estilo: Queda estrictamente prohibido el uso de @import dentro de archivos CSS para cargar recursos externos. Todos los archivos CSS se cargan como etiquetas <link rel="stylesheet"> independientes en el <head>, habilitando descargas paralelas.

5.3.6. Sincronización del Catálogo Compilado (SSOT MariaDB → catalog-compiled.js)

El catálogo de estudios (cat_estudios, cat_categorias, cat_gabinetes, cat_subgabinetes, cat_igabinetes, rel_estudio_gabinete, rel_igabinete_vinculos, top20_orden) tiene a MariaDB como Fuente Única de Verdad (SSOT). La clase \Common\CatalogBuilder::build() compila el estado completo del catálogo a un único archivo estático JS (catalog-compiled.js + alias legado idéntico catalog-data.js — no existen archivos separados por sub-dato). Ese único archivo expone todas las variables globales juntas: window.laeshCatalogData, laeshFlatCatalog, laeshTop20EstMed, laeshGabinetes, laeshSubgabinetes, laeshIGabinetes, laeshEstudioGabinete y laeshIGabineteVinculos. Flujo simplificado: escritura (live) → compilación (server) → aviso (push ligero) → descarga (pull)
  1. Escritura — vivo, POST a MariaDB. El admin guarda un cambio (Tabla 11) → transacción SQL directa contra cat_*/rel_*.
  2. Compilación — server-side, síncrono. Tras el COMMIT, el mismo request PHP llama CatalogBuilder::build(), que relee toda la BD y sobrescribe catalog-compiled.js en disco.
  3. Aviso — WebSocket, push de una señal, NO de los datos. CatalogBuilder::build() emite Notifier::emit('catalogo_actualizado', {titulo, mensaje}) — el payload es solo un título y un mensaje de ~100 bytes. El catálogo completo nunca viaja por el WebSocket.
  4. Descarga — HTTP, pull por el navegador. Cada navegador suscrito (Médicos, y Admin si tiene la pestaña de config abierta) recibe la señal vía ws-client.js y, en respuesta, hace una petición HTTP normal nueva: <script src="catalog-compiled.js?v=timestamp"> (cache-busting). Es el navegador quien jala el archivo completo — el WS solo dispara ese pull, no lo transporta.

5.4. Arquitectura de Autenticación y Autorización Criptográfica (JWT + JTI + OPcache RAM)

Para elevar la seguridad en el control de acceso y el ciclo de vida de las sesiones entre la web pública y los portales operativos (/laesh/md/, /laesh/rc/, /laesh/adrc/), se implementó una arquitectura híbrida de Tokens Criptográficos JWT respaldados por identificadores JTI únicos y Caché L2 en Memoria RAM (OPcache):

  • Firma HMAC-SHA256 y Emisión: Al autenticar credenciales en website/login/login.php vía Delight Auth, la clase \Common\JwtManager genera un token JWT firmado mediante algoritmo HS256 con la clave secreta LAESH_JWT_SECRET. Se transmite al cliente exclusivamente mediante la cookie segura laesh_jwt_token (banderas HttpOnly, SameSite=Strict y Secure bajo HTTPS).
  • Identificador Único JTI (UUID v4) y Persistencia: Cada token incluye un atributo jti único (UUID v4 de 256 bits). Este token se registra en la tabla jwt_jti_registry de MariaDB vinculando user_id, rol, IP del cliente, User-Agent, fecha de emisión (issued_at) y fecha de expiración (expires_at).
  • Verificación Ultra-Rápida en OPcache RAM (<0.1 ms): En cada petición HTTP a rutas sensibles, el middleware \Common\RbacManager::requirePermission() verifica el token JWT y consulta el estado del jti primero en la caché en memoria RAM de OPcache (Cache::get('JTI_' . md5($jti))). Si la clave existe en RAM y no está marcada como revocada, el acceso se autoriza inmediatamente en menos de 0.1 ms sin consultas SQL. Si no está en memoria (cache miss), consulta MariaDB (SSOT) y re-calienta la entrada en RAM.
  • Revocación Atómica / Force Logout Inmediato: Al cerrar sesión (logout.php) o mediante acciones de administración, se invoca JwtManager::revokeJti($jti) o JwtManager::revokeAllUserSessions($userId). Esto actualiza is_revoked = 1 en MariaDB e invalida la entrada en OPcache (opcache_invalidate), cerrando la sesión en tiempo real en todos los dispositivos del usuario sin esperar al vencimiento del token.
  • Mantenimiento Autónomo por Cron (05:00 AM): El script de mantenimiento diario de la caché (crons/cache_renew.php) ejecuta la purga automática de tokens expirados en MariaDB (DELETE FROM jwt_jti_registry WHERE expires_at < UNIX_TIMESTAMP()), manteniendo la tabla optimizada sin intervención manual.

6. Observabilidad y Trazabilidad de Fallos (Logs y Auditoría)

Siguiendo la directiva de robustez y resiliencia en entornos de red y base de datos locales inestables, el ecosistema LAESH cuenta con dos clases helper dentro del espacio de nombres \Common para el registro de auditoría, trazabilidad SQL y telemetría:

6.1. Log General del Sistema (Common\Logger)

La clase \Common\Logger gestiona la ingesta de alertas generales de la aplicación mediante una arquitectura de persistencia redundante (Dual‑Path) con filtrado de nivel mínimo configurable en caliente:

  • Ruta de Base de Datos (sys_logs): Guarda el nivel de severidad, mensaje, marca temporal y la IP del cliente. Asocia opcionalmente el user_id de Delight Auth para rastreo del operador.
  • Ruta Fallback Física (logs/app.log): Si la BD está offline, el log se redirige al archivo plano local para prevenir pérdida de eventos.
  • Filtro de Nivel Mínimo (producción): Logger::log() evalúa el nivel del mensaje contra el mínimo configurado antes de hacer ningún I/O. Implementado con LEVEL_ORDER (constante privada) y caché por request en $minLevel (propiedad estática): 
    DEBUG(0) → INFO(1) → WARN(2) → ERROR(3) → CRITICAL(4) → FATAL(5) → OFF(∞)

// En producción, nivel mínimo por defecto: WARN
// Logger::log('DEBUG', ...) y Logger::log('INFO', ...) → return temprano (sin BD, sin disco)
// Logger::log('WARN', ...)  → escribe en sys_logs + app.log
// Logger::log('ERROR', ...) → escribe en sys_logs + app.log
    El nivel se lee de /opt/laesh/configs/app-log-level.php (escrito por apply_log_levels.sh cuando el operador cambia log-levels.conf via el tab "Infra" de admrc/views/sistema.php). Si el archivo no existe → fallback a WARN. En entornos no-producción (APP_ENV !== 'production') → usa DEBUG automáticamente.

6.2. Trazabilidad y Telemetría de Fallos SQL (Common\DB::logFallback)

Inspirado en el motor de mitigación de fallos de Agua, la clase \Common\DB intercepta y registra de forma segura los fallos en la ejecución de transacciones y queries PDO:

  • Uso de Debug Backtrace: Emplea debug_backtrace() para indagar en la pila de ejecución y extraer automáticamente el archivo físico y la línea exacta de código que detonó la consulta (omitiendo los frames internos de la clase de base de datos).
  • Hash de Agrupamiento (CRC32): Genera un hash único de 8 caracteres hexadecimales derivado del CRC32 del string SQL original. Esto permite agrupar y contar incidencias duplicadas en los reportes de auditoría técnica.
  • Estructura fallback_log: Los registros fallidos se guardan en la tabla fallback_log con el texto SQL completo, el error nativo arrojado por el driver PDO (errorInfo) y el número de filas afectadas en operaciones de escritura.

2. Despliegue a Producción Servidor KVM2 / Nginx Sincronizar cambios de código PHP y base de datos con el servidor de producción laesh.mx.
3. Re-indexación Forzada Google Search Console 1. Ingresar a Search Console del dominio laesh.mx.
2. Pegar la URL https://laesh.mx/ en la herramienta superior de Inspección de URLs.
3. Hacer clic en «Solicitar indexación». Esto notifica inmediatamente a Googlebot para rastrear la página y actualizar los snippet de títulos, descripciones y horarios en Google Search.
4. Verificación de Rich Snippets Prueba de Resultados Enriquecidos de Google Introducir la URL pública para validar que las estructuras de MedicalLaboratory, GeoCoordinates y OpeningHoursSpecification cuenten con la aprobación de marcas verdes sin errores ni advertencias de sintaxis.
